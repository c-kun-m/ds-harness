# 01｜技术基线与上游锁定

> 模块编号：M01
> 功能前缀：`BASE`
> 优先级：P0
> 当前上游：`dsh-v0.1.2-alpha.4` / `4e84901e6471b79ec0338099867ebb4606d12bb5`

## 1. 模块目标

建立一套可复现、可验证、可升级、可回滚的技术基线。该基线确保桌面应用使用的 Harness Runtime、官方 Client、生成协议、兼容代码和数据格式始终属于同一个已验证 Release Set，避免 alpha 上游发生破坏性变化时以“能连上”为依据继续运行。

本模块不是简单记录依赖版本，而是定义：

- 哪些上游能力是正式接入面。
- 哪些能力不适合作为主 UI 通道。
- 如何取得、构建、验证和发布官方制品。
- 如何检测协议、能力和数据格式漂移。
- 如何对 Harness 升级进行预检、迁移与回滚。

## 2. 当前已核对的事实

| 项目 | 当前事实 | 对项目的约束 |
|---|---|---|
| 上游状态 | README 明确标注 developer preview，允许破坏性变更 | 禁止宽松版本和未经验证的自动升级 |
| 上游版本 | `@deepseek-ai/dsh-root@0.1.2-alpha.4` | Release Set 必须记录完整版本 |
| 上游提交 | `4e84901e6471b79ec0338099867ebb4606d12bb5` | 构建源必须精确到 Commit |
| Node 要求 | 上游为 `^22.19.0 || >=24.0.0`；本仓库为 `>=24 <25` | 工程统一 Node 24，Runtime 不依赖 Electron 内置 Node ABI |
| 包管理器 | 根项目 `pnpm@11.13.0`；上游 `pnpm@11.7.0` | 每个构建闭包使用自身锁定版本，不混用 Lockfile |
| 主服务 Profile | `dsh web --no-open --host 127.0.0.1 --port 0` | V1 使用官方 Web Host API，但不加载官方 Web 页面 |
| 就绪信号 | Host 输出 `dsh web: http://127.0.0.1:<port>/?token=<token>` | Supervisor 可以严格解析；原始行不得进入普通日志 |
| Unary | `/api/...` HTTP POST | Bridge 内统一超时、取消和错误映射 |
| Stream | `/api/remote.mux` WebSocket | Bridge 内维护 multiplex transport 和背压 |
| 认证 | 根路径 Token 换 HttpOnly/SameSite Cookie；Host/Origin 有保护 | Token 不是 Bearer；Cookie 只在 Bridge 内存中 |
| 网络 | 官方 Web Host 限制 loopback，拒绝 `0.0.0.0` | V1 不支持远程 Host 和 LAN |
| Session 数据 | 当前 `SESSION_FORMAT_VERSION=0`，无稳定迁移承诺 | Harness 升级前必须复制数据并预检，禁止直接原地尝试 |
| 许可证 | 上游根包声明 MIT；仍需递归收集第三方许可证 | 发布必须生成 SBOM 和 THIRD_PARTY_NOTICES |

权威源代码位于仓库内 `deepseek-harness/`。基线信息必须由自动脚本从实际源码、Lockfile 和构建制品重新生成，不可只依赖本文件中的文字。

## 3. 范围与非范围

### 3.1 范围

- Node、pnpm、TypeScript、Electron、Vue、Pinia、Vite、GSAP 和测试工具的锁定政策。
- 官方 Harness 源码、Runtime 制品、官方 Client 包和协议描述的锁定。
- Release Set Manifest、Hash、签名、SBOM、许可证和 Provenance。
- 协议/API/事件/Capability/Data Format 指纹。
- 上游兼容目录和升级流程。
- 开发、CI、打包、安装和运行时对基线的验证。

### 3.2 非范围

- 本文件不实现 Transport、Controller 或 UI。
- 不承诺兼容任意上游版本。
- 不建立对官方私有 `src/*` 路径的长期依赖。
- 不将上游源码目录作为用户运行时动态依赖。
- 不决定产品级更新 UX；更新流程由 `UPD-*` 功能负责。
- 不在这里修改官方源码；必要补丁必须独立、可审计、可重放。

## 4. 技术栈基线

### 4.1 已固定部分

| 层 | 技术 | 当前基线 | 锁定方式 |
|---|---|---|---|
| Workspace | pnpm workspace | `pnpm@11.13.0` | 根 `packageManager` + Corepack |
| Node | Node.js | `>=24 <25` | `.node-version`/CI 镜像/engines，后续具体 Patch 固定 |
| TypeScript | TypeScript | 根项目当前 `7.0.2` | 精确依赖 + Lockfile |
| Desktop | Electron | Spike 后选择经过验证的稳定精确版本 | `desktop-baseline.json` + Lockfile |
| Renderer | Vue 3 | Vue 3 当前稳定精确版本 | 精确依赖 + Lockfile |
| State | Pinia | 与 Vue 基线兼容的精确版本 | 精确依赖 + Lockfile |
| Router | Vue Router | 与 Vue 基线兼容的精确版本 | 精确依赖 + Lockfile |
| Build | Vite | 与 Electron 构建链验证后的精确版本 | 精确依赖 + Lockfile |
| Motion | GSAP 3 | 经过许可证和打包验证的精确版本 | 精确依赖 + Lockfile |
| Unit | Vitest | 根项目当前 `4.1.11` | 精确依赖 + Lockfile |
| E2E | Playwright | Spike 后选择与 Electron 基线兼容的精确版本 | 精确依赖 + Browser Cache Hash |
| Schema | TypeScript + Runtime Schema Library | Phase 0 评审后固定 | 精确依赖；所有边界必须运行时校验 |

“当前稳定版本”只允许出现在设计阶段文字中。进入实现后，`package.json` 不得使用 `latest`、`next`、Git branch、未固定 URL 或不受控的 `^`/`~`；所有生产依赖写入精确版本，最终解析结果由 frozen Lockfile 固定。

### 4.2 官方 Client 接入面

Utility Process 允许通过版本化兼容包使用以下官方 Client 面：

- `@deepseek-ai/dsh-client-connection/client`
- `@deepseek-ai/dsh-api-gateway/client`
- `@deepseek-ai/dsh-api-remotes/client`
- `@deepseek-ai/dsh-api-session-controller/client`
- `@deepseek-ai/dsh-api-workspace-controller/client`
- `@deepseek-ai/dsh-client-store`
- 经正式公共 export 暴露的 Headless Conversation 组件

兼容层之外禁止导入以上包；Renderer、Main 和 Preload 禁止导入任何 `@deepseek-ai/dsh-*` 或 Cordis 包。

### 4.3 不作为主 UI 通道的能力

| 方案 | 原因 | 允许用途 |
|---|---|---|
| 官方 SDK stdio | 当前缺少完整 mid-turn cancel、session close、Approval 等 UI 必需语义 | 自动化测试、诊断工具 |
| ACP | 面向标准化 Agent 自动化，不保留完整 DSH Presentation 和回放能力 | 后续第三方集成 |
| 官方 React Web UI | 与 Cordis 动态插件和官方页面组合耦合，不是独立 Vite App | 对照行为、差分测试 |
| 上游私有 `src/*` | 不属于稳定公共 API，升级极易破坏 | 仅限有退出计划的 Spike，GA 禁止 |

## 5. 依赖

### 5.1 前置依赖

- 对应 Tag/Commit 的官方源码仓库。
- 可验证的源码来源和 Git Object。
- 可复现构建工具链或官方签名发布制品。
- 平台代码签名和发布基础设施。

### 5.2 下游消费者

- Runtime Supervisor 使用 Runtime Manifest、Hash、入口和平台约束。
- Harness Bridge 使用官方 Client 版本、协议指纹和 Compat ID。
- Updater 使用完整 Release Set、数据兼容范围和 Rollback Pair。
- Diagnostics 展示版本清单，但不得展示 Secret 或私有路径。
- CI 使用 Lockfile、Dependency Policy、SBOM 和协议差异检查。

## 7. Release Set 状态与数据模型

### 7.1 Release Set Manifest

```ts
type ReleaseSetManifest = {
  schemaVersion: 1;
  releaseSetId: string;
  app: {
    version: string;
    commit: string;
    channel: "internal" | "beta" | "stable";
  };
  toolchain: {
    node: string;
    pnpm: string;
    electron: string;
    typescript: string;
  };
  harness: {
    version: string;
    tag: string;
    commit: string;
    sourceTreeHash: string;
    runtimeSha256: string;
    platform: "win32-x64" | "darwin-arm64" | "linux-x64";
    entrypoint: string;
    sessionFormatVersion: number;
  };
  clients: Record<string, { version: string; integrity: string }>;
  compatibility: {
    compatId: string;
    protocolFingerprint: string;
    capabilityFingerprint: string;
    eventFingerprint: string;
    projectionFingerprint: string;
  };
  patches: { id: string; sha256: string; purpose: string }[];
  supplyChain: {
    lockfileSha256: string;
    sbomSha256: string;
    noticesSha256: string;
    signature?: string;
  };
};
```

### 7.2 兼容状态机

```text
UNVERIFIED
  → SOURCE_VERIFIED
  → BUILT
  → CONTRACT_VERIFIED
  → DATA_PREFLIGHT_VERIFIED
  → SIGNED
  → RELEASE_ELIGIBLE

任意内容变化 → INVALIDATED
```

Hash、依赖、Patch 或协议描述任一变化都使后续状态失效，必须从相应阶段重新验证。

### 7.3 运行时兼容判定

```ts
type CompatibilityResult =
  | { kind: "COMPATIBLE"; releaseSetId: string }
  | { kind: "APP_UPDATE_REQUIRED"; expected: string; actual: string }
  | { kind: "RUNTIME_REPAIR_REQUIRED"; artifact: string }
  | { kind: "DATA_MIGRATION_REQUIRED"; from: number; to: number }
  | { kind: "UNSUPPORTED_EXTERNAL_RUNTIME" }
  | { kind: "TAMPERED"; supportCode: string };
```

只有 `COMPATIBLE` 可以继续认证和加载 Session。

## 8. 功能合同

| ID | P | 开发/用户行为 | 实现方式与接口 | 错误恢复与安全 | 测试要求 | Definition of Done |
|---|---|---|---|---|---|---|
| `BASE-001` | P0 | 所有环境得到同一个上游源码 | 用 Tag+40位 Commit+source tree hash 锁定；生成 `upstream.lock.json` | Commit/Tree 不符立即失败，不自动 fetch 任意 branch | 在干净 clone、篡改文件、错误 Tag 上验证 | CI 和本地 verifier 对同一源码给出同一结果 |
| `BASE-002` | P0 | App 只运行匹配 Release Set 的 Harness | Manifest 记录 Runtime SHA-256、平台、入口和签名 | 缺失/损坏/平台错误进入 Repair Required，不尝试执行 | 单字节篡改、替换入口、错误架构、签名失效测试 | 所有非法制品启动前被拒绝 |
| `BASE-003` | P0 | 官方 Runtime 与 Client 永远锁步 | Client 包版本和 integrity 写入 Manifest；Compat 注册表按 releaseSetId 选择 | 混合版本 fail closed，不做鸭子类型兼容 | 交叉组合 Runtime/Client 的负向矩阵 | 只有已批准组合通过启动握手 |
| `BASE-004` | P0 | 协议发生变化时团队在合并前知道 | 对 Typert Remote descriptor、方法签名、Stream 和事件 allowlist 生成规范化指纹 | 生成器变化需人工确认；差异报告不得包含 Secret fixture | Golden fingerprint、顺序扰动、真实升级 Diff 测试 | 每次上游升级产出可评审的语义差异报告 |
| `BASE-005` | P0 | UI 不会因 Capability 缺失而展示危险动作 | 建立 capability manifest，Bridge 握手后只发布验证能力 | 未知/缺失能力默认关闭；不能以版本字符串猜能力 | 缺失、额外、类型改变的 Capability 合同测试 | 每个 P0/P1 UI 动作有明确 Capability 来源 |
| `BASE-006` | P0 | Harness 数据不会被不兼容版本原地损坏 | 记录 Session/Data format；升级前在副本上 preflight | 格式未知时只读/阻断；旧 Runtime 禁止打开升级副本 | v0 fixture、损坏 journal、升级失败、降级测试 | 数据预检和回滚证据进入 Release Set |
| `BASE-007` | P1 | 开发和 CI 使用一致工具链 | 固定 Node Patch、pnpm、Electron 和构建镜像 digest | 检测到不同版本时给出修复命令并停止构建 | Windows/Linux CI 和干净 VM bootstrap | `verify:baseline` 在全部受支持环境通过 |
| `BASE-008` | P1 | 依赖升级可被审计和重现 | 精确版本、frozen lockfile、依赖 allow/deny policy | Lockfile 漂移、Git/HTTP 动态依赖和安装脚本例外均阻断 | Lockfile 重建、离线缓存、恶意依赖规则测试 | 相同输入产生相同依赖树和制品 Hash，平台差异有记录 |
| `BASE-009` | P1 | 必要上游修改保持最小、透明、可移除 | Patch 每项拥有 ID、目的、上游 Issue、基线 Hash 和适用版本 | Patch 应用失败立即停止；禁止人工修改后继续构建 | Patch 重放、反向移除、上游已合并检测 | 每个 Patch 可独立应用/撤销且有退出条件 |
| `BASE-010` | P1 | 上游升级不会扩散到 Vue 和 Electron 其他层 | 每个上游族使用 `harness-compat/vX_Y_Z`，对外只返回 Desktop DTO/Patch | 新旧适配器并存验证；禁止跨目录共享官方类型 | Compat 消费者合同和静态依赖检查 | 上游升级只修改 compat、fixture、manifest 及必要合同版本 |
| `BASE-011` | P1 | 发布者知道制品包含什么以及许可证义务 | 生成 CycloneDX/SPDX SBOM、THIRD_PARTY_NOTICES 和依赖许可证报告 | 未识别/不允许许可证阻断发布；报告不含本地路径 | SBOM 完整性与安装制品反向比对 | SBOM 可覆盖 App 和 bundled Runtime 的全部组件 |
| `BASE-012` | P1 | 官方能力事实可以被重新核对 | 保留 capability probe、真实 Host 合同 fixture 和来源定位 | Probe 不执行业务写操作；临时环境隔离 | 在固定 Runtime 上重复运行得到稳定结果 | 能力报告包含方法、事件、Stream、限制和证据 Hash |
| `BASE-013` | P1 | 诊断页面可准确展示版本且不泄漏环境信息 | Bridge/Main 发布脱敏 `VersionInfoDto` | 不展示 Token、Home 绝对路径、用户名和完整环境变量 | Snapshot、PII/Secret scan | 用户能复制支持信息，内容与 Manifest 一致且已脱敏 |
| `BASE-014` | P1 | 团队以受控流程升级上游 | 新建 upgrade branch，生成 Diff，运行协议/投影/数据/性能/回滚门禁 | 任一 P0 失败即停止；旧 Release Set 保留到新版本稳定 | 模拟无变化、兼容变化、破坏变化三种升级 | Upgrade Report 获批准并绑定新 Release Set |
| `BASE-015` | P2 | 发布通道不会交叉污染配置和数据 | Internal/Beta/Stable 使用独立 appId、更新源、用户数据目录和 Release Key | 通道切换必须显式迁移，不能直接共享可写 Home | 多通道并存、误装、降级、卸载测试 | 三通道可并存且互不读取/覆盖数据 |
| `BASE-016` | P2 | 团队可追溯每个制品的构建来源 | 保存源码 Commit、构建器 digest、命令、时间、CI identity 和签名证明 | 本地未证明制品不能进入 Stable | Provenance 校验、重建对比 | Stable Artifact 拥有完整可验证 Provenance |

## 9. 协议与能力锁定明细

指纹生成必须至少覆盖：

1. Session：list、search、create、selectModel、modelCatalog、open path、rename、fork、prompt、attachment、updateQueue、cancel、page、follow、control。
2. Workspace：create、rename、delete、insertBefore、insertSessionBefore、archiveSession、follow、directory picker。
3. Interaction：approval request、user question request 以及响应合同。
4. Settings：settings、credentials、provider/model discovery 和更新事件。
5. Subagent：list、prompt、interruptByParent。
6. Goal：create、edit、pause、resume、complete、clear。
7. 事件：Session status/activity/add/remove/error 以及设置、凭据、LLM 更新。
8. Conversation：节点种类、Tool call/result 关联、最终状态和可见语义。

规范化时只忽略与语义无关的对象键顺序；不能忽略 optional/required、类型联合、事件模式、流方向和错误语义。

## 10. 上游升级流程

### Step 1：登记候选版本

- 记录来源、Tag、Commit、Release Notes 和安全公告。
- 冻结旧 Release Set，不在原 Compat 目录上直接修改。

### Step 2：生成静态差异

- 包版本和依赖差异。
- Remote 方法、参数、返回值、Stream 和事件差异。
- Session/Data format 和 persistence 差异。
- License、native dependency 和平台矩阵差异。

### Step 3：建立新 Compat

- 新建版本目录。
- 更新官方类型到 Desktop DTO 的映射。
- 保留旧 fixture，新增新版本 fixture。
- 不让官方类型穿过 Utility 边界。

### Step 4：运行动态合同

- 启动/认证/关闭。
- 全量 Unary/Stream capability probe。
- Prompt、Cancel、Approval、Question、History、Gap Repair。
- Conversation differential replay。
- 旧数据副本 preflight。

### Step 5：运行产品回归

- 所有 P0/P1 E2E。
- 性能基准对比。
- 安全扫描和 SBOM。
- 更新、启动失败和回滚演练。

### Step 6：签署 Release Set

- 只有所有门禁通过才生成签名 Manifest。
- 新 Release Set 进入 Internal/Beta；稳定观察结束后才能进入 Stable。

## 11. 开发顺序

1. 实现 `ReleaseSetManifest` Schema 和示例。
2. 从当前上游生成 `upstream.lock.json`。
3. 实现源码/Runtime/Lockfile Hash verifier。
4. 实现 Remote、事件、Capability 和投影指纹工具。
5. 建立当前 `v0_1_2` Compat 注册项。
6. 建立固定 Runtime 的 capability probe。
7. 建立数据 fixture 和 preflight harness。
8. 建立 SBOM、许可证和 Provenance 生成。
9. 将全部 verifier 接入 CI、打包和运行时启动。
10. 用一个人为破坏的候选版本演练完整升级阻断。

每一步单独测试、单独提交；前一步未达到 DoD 时不允许将其结果作为下一步信任输入。

## 12. 验收清单

- [ ] 当前 Tag、Commit、包版本和 Node 要求可由工具从上游重新验证。
- [ ] Electron/Vue/GSAP 等实际实现依赖最终均为精确版本且有 frozen Lockfile。
- [ ] Release Set Manifest 包含 App、Runtime、Client、Compat、协议、数据、Patch、SBOM 和签名信息。
- [ ] Runtime 或 Client 混合版本会在认证前被拒绝。
- [ ] 协议、事件、Capability 和 Conversation 投影均有独立指纹或差分证据。
- [ ] Renderer/Main/Preload 的依赖规则禁止官方包和 Cordis。
- [ ] Session format 未知时不会原地打开数据。
- [ ] 所有 Patch 都有用途、Hash、适用版本和退出条件。
