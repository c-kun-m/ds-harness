# 15：测试、性能与质量门禁

## 1. 文档目标

本文件定义 UI 桌面项目的测试体系、性能预算、持续集成门禁和发布质量证据。测试必须覆盖真实安装形态和真实官方 Harness，不能只通过调用内部函数或 Vite 开发服务器证明系统可用。

测试工程从 Phase 0 开始建设，与业务代码同步演进。任何功能的 Definition of Done 都必须包含正常路径、失败路径、取消、恢复、安全和资源清理证据。

## 2. 测试环境分层

| 环境 | 用途 | 是否使用真实 Electron | 是否使用真实 Harness |
|---|---|---:|---:|
| Unit | Schema、Reducer、状态机、纯算法 | 否 | 否 |
| Component | Vue 组件、交互、可访问性 | 否/浏览器 | 否 |
| Fake Host Integration | 故障、乱序、限额、竞态 | 部分 | 否 |
| Real Contract | 官方协议与 Controller 合同 | 可选 | 是，固定 commit |
| Electron E2E | 完整进程与用户流程 | 是 | 是或确定性 Fake Model |
| Packaged E2E | 安装、签名、更新、回滚 | 是，正式制品 | 是 |
| Performance/Soak | 长会话、事件风暴、泄漏 | 是，Release 构建 | 是/Replay |

## 3. 测试基础设施功能

### TEST-001：桌面测试支持包

建议目录：

```text
packages/test-support/desktop/
packages/test-support/fake-harness/
packages/test-support/fixtures/
packages/test-support/security-corpus/
apps/desktop/e2e/
```

**实现方式**：

- 每个用例创建独立临时 Harness Home、工作区、日志目录和端口空间。
- 提供 fake clock、deferred promise、barrier 和显式事件探针，禁止用随意 `sleep` 猜测竞态顺序。
- 统一登记子进程、端口、Socket、Timer、Listener、Worker、Object URL 和临时目录；用例结束逐项检查归零。
- Readiness Parser 在测试输出前脱敏 Token；CI artifact 不保存原始 Harness stdout。
- Windows 测试必须在原生 PowerShell/Runner 执行进程树和安装验证。

**DoD**：连续 100 次启动/关闭测试环境，无孤儿进程、占用端口、残留 Listener 和凭据泄漏。

### TEST-002：Fake Harness 与故障代理

Fake Host 必须能脚本化以下行为：正常 unary、正常 stream、401/403、延迟、超时、帧丢失、重复、乱序、半开 WebSocket、慢消费、Gap、认证失效、Host 崩溃、超大消息和无效 Schema。

它必须使用与 `desktop-contracts`、官方 Remote fixture 相同的测试数据，但不得被当作真实官方兼容性的唯一证据。

**DoD**：每个 Bridge 状态和错误码都能通过确定性脚本触发；测试无需真实模型 API Key。

### TEST-003：Golden Session Fixtures

固定包含：

- 普通文本与多段 Reasoning。
- 高频 `assistant/chunk`。
- 交错、缺一端和重复的 Tool call/result。
- Retry、Cancel、Interrupted、Error、Compaction。
- Approval、User Question、Queue、Steer。
- Subagent、Goal、未知 ignorable event 和未知 required event。
- 历史分页边界与 Packed Chunk Rows。
- 中文、Emoji、RTL 样例、超长代码、Markdown、Diff、ANSI。

Fixture 必须记录来源 Harness tag/commit、数据格式和期望语义 Snapshot。

## 4. 测试类型与功能规格

### TEST-004：单元测试

覆盖：IPC Schema、状态转换、错误映射、日志脱敏、URL/路径校验、Runtime Manifest、Readiness Parser、背压队列、Patch 应用、滚动状态机、Tool Presenter 解析、GSAP cleanup、更新状态机。

门禁：安全、兼容、投影、更新模块行覆盖不低于 90%、分支不低于 85%；全仓库行覆盖不低于 80%、分支不低于 75%。覆盖率不能替代关键状态和失败断言。

### TEST-005：属性与 Fuzz 测试

使用生成式测试覆盖任意 JSON、深层 Error、循环替代结构、重复/乱序/丢失事件、非法 generation/revision、超长 URL、混合路径分隔符和极端尺寸。

必须验证：

- Replace 幂等。
- Revision 只能连续前进或触发 Resync。
- 旧 Generation 永远不改变当前状态。
- 每个 Interaction 最多完成一次。
- 不确定写操作永远不被自动重放。
- 队列和递归渲染始终有界。

### TEST-006：官方协议合同测试

**实现方式**：

1. 启动固定版本真实 `dsh web --port 0 --no-open`。
2. 完成 Token/Cookie 认证。
3. 对 UI 使用的每个官方 Remote 方法执行成功、拒绝、取消、断线场景。
4. 记录 Remote/事件/Schema 指纹并与 `upstream.lock.json` 对比。
5. 上游升级 PR 自动生成新增、删除和变化清单。

**DoD**：未分类 API/Schema 差异为零；版本错配明确失败；Fake Host 测试和真实合同测试均通过。

### TEST-007：Conversation 差分测试

同一 Golden Session 输入官方 Web Conversation Projection 与桌面 Headless Projection，比较用户可见语义而非 DOM：节点顺序、文本块、Reasoning、Tool 配对、Turn 终态、Retry、Compaction、Approval、Subagent 和分页边界。

允许差异必须进入版本化差异账本，说明原因、用户影响和责任人。不得用忽略 Snapshot 字段掩盖关键差异。

### TEST-008：Bridge 与真实集成测试

使用真实 Main/Utility 或等价进程边界，覆盖认证、unary、mux stream、cancel、backpressure、Renderer reload、Bridge crash、Harness restart、generation reset 和 Snapshot resync。

**DoD**：重连后不丢、不重、不乱序；取消在 UI、Bridge、Harness 三层终态一致；20 次连接/断开后资源回到基线。

### TEST-009：Vue 组件与视觉测试

组件测试覆盖 App Shell、Sidebar、Conversation、Composer、Approval、Question、Tool Card、Inspector、Settings、Recovery Mode。模拟 RAF、ResizeObserver、IntersectionObserver、Worker 和 MessagePort。

视觉回归覆盖 Light、Dark、System、Forced Colors、zh-CN、en-US、伪语言、200% Zoom、长文本、错误态、Reduced Motion 和不同 DPI。视觉基线变化必须人工审核。

### TEST-010：无障碍测试

自动 axe 扫描结合纯键盘、中文 IME、NVDA 人工流程；macOS 发布后增加 VoiceOver。测试创建 Workspace、发送 Prompt、取消、处理 Approval、回答 Question、查看 Tool 和导出诊断的完整流程。

**DoD**：严重/高等级自动问题为零；关键流程无需鼠标；焦点不会落入已虚拟卸载元素；Reduced Motion 下功能完整。

### TEST-011：Electron 与打包制品 E2E

使用 Playwright Electron 驱动 Release 构建；RC 还必须驱动真实安装包。覆盖首次启动、中文/空格路径、既有数据、网络故障、Runtime 崩溃、应用退出、升级和卸载。

**DoD**：核心路径连续 100 次通过；RC 安装主流程连续 20 次通过，禁止靠自动重试把失败改成成功；退出后规定时间内所有进程消失。

### TEST-012：安全回归

覆盖 IPC 越权、sender spoof、路径穿越、symlink、XSS、Markdown/KaTeX、恶意 SVG、ANSI OSC、畸形 Diff、危险 URL、Cookie/Token canary、Runtime 篡改、更新 Manifest 篡改和依赖投毒。

**DoD**：Critical/High 问题为零；例外必须有书面 Owner、缓解措施和不超过 30 天的失效日期，且数据/凭据泄漏类问题不得例外发布。

### TEST-013：故障注入与恢复

必须在这些时刻注入故障：Readiness 分片、认证、创建 Session、Prompt admission、流式中、Tool 运行中、Approval 待处理、历史 Prepend、持久化 Flush、更新下载、数据复制、原子切换。

每个故障需要断言：最终稳定状态、错误码、用户恢复动作、数据完整性、进程清理和重启后的状态。不能确定写结果时必须进入 `OUTCOME_UNKNOWN`。

### TEST-014：长稳与资源泄漏

Release 构建执行 8 小时 PR/Nightly 缩短版和 24–48 小时 RC 版，循环发送、取消、Session 切换、分页、重连、Renderer reload、Bridge restart 和 Harness restart。

记录 Heap、Working Set、DOM、Listener、Timer、Socket、Worker、GSAP Tween 和子进程。Release blocker 测试不得 quarantine。

## 5. 性能基线与预算

### PERF-001：参考环境

V1 固定参考机：Windows 11 x64、4 核/8 线程、16 GiB RAM、NVMe、集成显卡、1080p、100%/200% 缩放。性能 CI 使用专用稳定 Runner；公共负载不确定 Runner 只做功能测试。

基准数据：20 个 Workspace、10,000 个 Session 索引、1,000 Turn、25,000 Event、5,000 event/s 风暴、10 MiB Diff、长 ANSI 输出和多附件。

基线脚本、系统镜像、数据 Seed 和测量区间必须版本化。

### PERF-002：启动性能

| 指标 | V1 门禁 |
|---|---:|
| Electron Shell 冷启动 p95 | ≤ 2.5 s |
| Harness Ready p95 | ≤ 5 s |
| 完整可交互 p95 | ≤ 6 s |
| 子进程异常退出识别 | ≤ 1 s |

超时必须进入可诊断状态，不能无限显示 Loading。

### PERF-003：输入和流式性能

| 指标 | V1 门禁 |
|---|---:|
| 本地 Prompt 回显 p95 | ≤ 16.7 ms |
| Harness Event 到可见 Tail p95 | ≤ 100 ms |
| Harness Event 到可见 Tail p99 | ≤ 250 ms |
| 输入响应延迟 p95 | ≤ 100 ms |
| 稳态流式主线程任务 p95 | ≤ 8 ms |
| 事件风暴 | 5,000 event/s 持续 60 s 不 OOM、不丢终态事件 |

语义边界、Final、Error、Approval 不得合并丢弃；同一文本块的 Delta 最多每帧发布一次，后台 Session 可按 100–250 ms 合批。

### PERF-004：长会话与滚动

| 指标 | V1 门禁 |
|---|---:|
| 1,000 Turn / 25k Event 顶层 DOM 行 | ≤ 160 |
| Prepend 阅读锚点误差 | ≤ 2 px |
| 滚动帧耗时 p95 | ≤ 16.7 ms |
| 稳态 Long Task | 无 > 100 ms |
| Session 缓存切换 p95 | ≤ 100 ms |

### PERF-005：Worker、Bundle 与懒加载

- Markdown、Shiki、Diff、大 JSON 格式化进入 Worker。
- Worker 返回携带 session epoch、node key 和 revision；晚到结果直接丢弃。
- Shiki Grammar、KaTeX、完整 Diff Inspector 和未来 xterm 必须懒加载。
- Renderer 首屏 JavaScript 预算：raw ≤ 1.5 MiB、gzip ≤ 450 KiB。
- 重型解析不能在主线程产生超过 50 ms 的单任务。

### PERF-006：内存与后台资源

初始预算在 Phase 0/1 基线后允许通过 ADR 调整：

| 指标 | 初始上限 |
|---|---:|
| Renderer 空闲 Heap | ≤ 120 MiB |
| 1,000 Turn Renderer Heap | ≤ 250 MiB |
| 应用整体空闲 Working Set | ≤ 450 MiB |
| 重负载 Working Set | ≤ 750 MiB |
| 后台无活动流 CPU | < 2% |

20 次 Session 打开/关闭和重连后，强制 GC 的内存相对稳定基线增长不得超过 15%；Timer、Listener、Worker、Socket 和 Tween 不得随循环次数线性增长。

### PERF-007：性能回归门禁

- PR 运行小数据 Smoke；主分支/Nightly 运行完整 Replay；RC 运行专用机器长稳测试。
- 同时比较绝对预算和最近 Stable 基线。
- 任一关键指标退化超过 10% 或突破绝对预算时失败。
- 更新基线必须附带 Trace/Flamegraph/Heap 证据、原因和人工审批，不能仅重录数字。

## 6. CI 流水线

### 快速 PR 流水线

format → lint → typecheck → dependency-boundary → unit → property → contract-diff → build → secret/license/security scan。目标 p95 不超过 12 分钟；不接触签名和发布凭据。

### 主分支流水线

在 PR 基础上运行真实 Harness Integration、Vue Browser Test、Electron E2E 和未签名打包 Smoke。目标 p95 不超过 30 分钟。

### Nightly 流水线

运行完整 E2E、故障注入、性能 Replay、Heap/资源检查、依赖审计和上游兼容 Diff。目标不超过 2 小时。

### RC 流水线

隔离签名 Runner 构建制品，生成 SBOM/Provenance/Hash，签名后再次执行 Clean Install、启动、更新、回滚和卸载测试。Internal、Beta、Stable 必须推广同一个已签名制品，禁止重新构建。

## 7. 功能 Definition of Done

任何功能 ID 标记为完成前，都必须具备：

1. 接口和状态机已写入对应模块文档。
2. 正常、空状态、加载、失败、取消和恢复行为已实现。
3. 输入输出通过运行时 Schema 校验并有容量上限。
4. 单元测试与对应级别的集成/E2E 已通过。
5. 日志字段已登记且通过 Secret 扫描。
6. 键盘和基础无障碍行为已验证。
7. 资源释放和重复进入测试已通过。
8. 功能追踪矩阵已有代码位置、测试位置和验收证据。
9. 变更形成一个主题明确、通过正常 Hook 的 Git 提交。

## 8. 开发顺序与退出门禁

1. **Phase 0**：先实现 TEST-001～TEST-003 和 PERF-001，固定临时 Harness Home、Fake Host、Golden Fixtures、参考机器与基线数据；测试环境无法确定关闭时停止后续开发。
2. **Phase 1～2**：实现 TEST-004～TEST-007，建立运行时 Schema、状态机属性测试、官方协议指纹和 Conversation 差分；未分类上游差异为零后才能冻结 Desktop Contract。
3. **Phase 3～5**：实现 TEST-008、PERF-002～PERF-003，真实覆盖 Electron、Utility、Harness 生命周期、认证、重连、背压与流式；没有真实 Harness 证据时不得进入 Alpha。
4. **Phase 6～9**：实现 TEST-009～TEST-010、PERF-004～PERF-006，随每个界面切片同步补组件、视觉、键盘、NVDA、长列表、Worker、内存和 GSAP 清理测试。
5. **Phase 10**：完成 TEST-011～TEST-014 和 PERF-007，使用最终打包/签名制品执行安全、故障、安装、升级、回滚和 24～48 小时 Soak。
6. **Phase 11**：仅推广已通过全部门禁的同一签名制品；Beta/GA 观察发现阈值退化时停止推广并保留可回滚版本。

每一阶段的测试基础设施必须先于或与被测功能同时完成。不得把 Fake Host 成功当作官方兼容成功，不得把 Vite 页面成功当作 Electron 制品成功，也不得以扩大超时、自动重试或更新基线掩盖失败。

## 9. 发布质量总门禁

- [ ] Must 功能追踪矩阵 100% 完成，无缺失映射。
- [ ] 官方协议差异全部分类。
- [ ] P0/P1 缺陷为零。
- [ ] Critical/High 安全问题为零。
- [ ] Token、Cookie、API Key 泄漏为零。
- [ ] 核心 E2E 连续运行达到门槛。
- [ ] 性能全部满足绝对预算且无超过 10% 的未解释退化。
- [ ] 24–48 小时 RC Soak 无崩溃、未处理 Reject 和持续资源增长。
- [ ] 安装、升级、回滚和卸载均在干净 VM 通过。
- [ ] 最终签名制品与测试制品 Hash 一致。

## 10. 模块完成定义

本模块完成需要：TEST-001～TEST-014 与 PERF-001～PERF-007 全部达到 `VERIFIED`；每个 P0/P1/P2 产品功能至少映射一个正常路径和一个风险相称的失败路径测试；官方合同、差分、Electron E2E 与 Packaged E2E 均真实运行；覆盖率、性能、资源、无障碍、安全和 Soak 门禁无未批准例外；所有报告绑定最终 Release Manifest、源码 Commit、Runner 环境和制品 Hash，并能在干净环境重放。
