# 16：打包、更新、迁移与回滚

## 1. 文档目标

本文件定义桌面应用从源码到可验证安装包的完整发布链路，以及应用、官方 Harness Runtime、官方 Client、兼容层和用户数据如何原子升级与安全回滚。

核心原则：桌面应用和 Harness 是一个经过兼容验证的版本组；更新失败不得破坏当前可运行版本，旧 Runtime 不得静默打开被新版本写入的数据。

## 2. 数据分类与所有权

| 数据 | 真源 | 可否重建 | 备份/迁移策略 | 删除权限 |
|---|---|---:|---|---|
| Harness Home / Session | 官方 Harness | 否 | 更新前 Copy-on-Upgrade | 用户明确确认 |
| Workspace 索引 | 官方 Harness | 通常否 | 随 Harness Home 备份 | 用户明确确认 |
| 桌面 UI 偏好 | Desktop App | 是 | Schema 迁移，失败可重置 | 设置页可重置 |
| 草稿 | Desktop App | 部分 | 按 Session 存储并版本化 | 用户或 LRU 策略 |
| Renderer Cache | Desktop App | 是 | 不迁移 | 可自动清理 |
| 日志/指标 | Desktop App | 是 | 不迁移，按保留期轮转 | 可清理 |
| 诊断包 | 用户导出 | 是 | 用户指定位置 | 用户管理 |
| Provider Secret | OS Keychain/Harness Provider | 否 | 不复制明文，保留引用/重授权 | 用户明确删除 |
| 下载中的更新 | Updater | 是 | 校验后使用，失败丢弃临时文件 | 可自动清理 |

任何新增持久数据必须补充：Schema Version、Owner、可重建性、备份、迁移、删除和降级行为。

## 3. 发布身份

### PKG-001：统一 Release Manifest

每个制品必须携带并在诊断页展示：

```text
appVersion
buildId
gitCommit
electronVersion
embeddedNodeVersion
harnessVersion
harnessTag
harnessCommit
harnessRuntimeSha256
officialClientVersions
protocolFingerprint
compatVersion
uiProtocolVersion
conversationProjectionVersion
sessionFormatVersion
platform
architecture
updateFormatVersion
```

**实现要求**：Manifest 在构建阶段从锁文件和真实制品生成，禁止手工重复填写；启动时由 Main、Runtime Supervisor 和 Bridge 分别校验自己关心的字段。

**DoD**：任一字段缺失、Hash 不匹配或组合未进入兼容清单时，应用进入 `UPDATE_REQUIRED/RECOVERY_MODE`，不得半兼容运行。

### PKG-002：上游与 Runtime 制品

- 开发源码使用固定 commit 的 submodule 或只读 vendor source。
- 正式安装包只携带经过发布流水线构建、签名和 Hash 登记的 Runtime。
- Runtime 放置在 `extraResources`，不塞入 ASAR，不依赖用户系统 Node。
- 主程序启动 Runtime 前再次校验文件身份。
- Windows 首版只选择 win-x64 制品；不做运行时猜测或跨架构回退。

## 4. 构建与打包功能

### PKG-003：分目标构建

构建顺序：

1. 生成 Desktop Contracts 和版本 Manifest。
2. 构建 Bridge Utility 及对应 compat。
3. 构建 sandboxed Preload。
4. 构建 Electron Main。
5. 构建 Vue Renderer 静态资源。
6. 校验依赖边界和 Source Map 策略。
7. 装配 ASAR、Runtime 与许可证。
8. 注入并验证 Electron Fuses。
9. 生成未签名制品、SBOM、Hash 和 provenance。
10. 在隔离环境签名，再对最终制品做 E2E。

Main、Preload、Bridge 和 Renderer 必须使用独立入口及构建配置。生产包不得包含测试凭据、开发服务器地址、Harness 启动 Token或可被普通用户加载的源码映射。

### PKG-004：安装与卸载

**首次安装**：创建应用目录和用户数据目录，但不预先创建虚假 Workspace/Session；首次运行再完成 Runtime 校验和初始化。

**升级安装**：不得覆盖正在运行的 Runtime；必须先由应用完成 drain、数据预检和退出，再由安装器替换版本。

**卸载**：默认删除程序文件和缓存，不自动删除 Harness Home、Session、用户导出的诊断包和 OS Keychain Secret；提供明确的“同时删除所有用户数据”选项及二次确认。

**DoD**：Clean Install、Repair、Upgrade、Uninstall、保留数据重装均在干净 VM 验证；路径包含中文、空格和长路径时通过。

### PKG-005：签名、SBOM 与供应链证明

- Windows EXE/DLL/Installer 全部 Authenticode 签名并使用可信时间戳。
- 签名密钥只存在于 HSM、Trusted Signing 或隔离签名服务。
- 生成 CycloneDX/SPDX SBOM、第三方许可证和每个二进制的 SHA-256。
- 发布 Provenance 记录源码 commit、lockfile hash、Runner image、工具版本和构建任务。
- 签名前后分别扫描恶意软件、秘密、调试入口和未登记二进制。

**DoD**：最终下载制品的签名、Manifest 和 Hash 全部可离线验证；Fork PR 和普通 CI 无法读取签名凭据。

## 5. 更新功能规格

### UPD-001：更新渠道

渠道固定为 `internal → beta → stable`：

- 使用不同 appId、更新源、用户配置目录和 Harness Home。
- 同一个已签名制品在渠道之间推广，不重新构建。
- Stable 默认不自动升级 Harness Runtime，除非该版本通过数据预检和回滚门禁。
- 支持签名 Kill Switch 停止问题版本继续扩散，但不能远程删除用户数据。

### UPD-002：更新状态机

```text
IDLE
→ CHECKING
→ AVAILABLE
→ DOWNLOADING
→ VERIFYING
→ READY_TO_INSTALL
→ DRAINING
→ INSTALLING
→ COMPLETE

任意中间态 → ERROR
INSTALLING/启动验证失败 → ROLLED_BACK 或 RECOVERY_REQUIRED
```

每次转换记录版本、原因、进度、重试策略和 correlation ID。UI 不得把“下载完成”展示成“安装完成”。

### UPD-003：更新类型

| 类型 | 变化范围 | 策略 |
|---|---|---|
| A | 仅 UI，Runtime/协议/数据不变 | 可快速更新和二进制回滚 |
| B | App、Client、Compat、Runtime 锁步变化，数据格式不变 | 原子版本组更新 |
| C | Harness 或桌面持久数据格式变化 | 必须 Copy-on-Upgrade、迁移预检和人工灰度 |

每个 Release 必须声明类型；无法判断时按 C 类处理。

### UPD-004：下载与验证

- Manifest 和制品分别验签，校验渠道、平台、架构、版本单调性和 Hash。
- 下载到版本化 staging，支持分块、断点续传和磁盘配额。
- 默认拒绝降级和旧 Manifest 重放；应急降级需单独签名授权。
- 下载或验证失败只删除临时制品，不影响当前安装。

**DoD**：截断下载、错误 Hash、过期/重放 Manifest、错误平台、签名链失败均不会进入 READY_TO_INSTALL。

### UPD-005：安装前 Drain

1. 停止接受新 Prompt、Queue 修改和新 Approval。
2. 检查当前 Turn、Tool、Subagent、持久化和文件操作。
3. 用户选择等待完成或明确取消；不静默中止工作。
4. Bridge 停止新 RPC，关闭 streams，并等待官方 Controller dispose。
5. Supervisor 触发 Harness 正常 flush/stop。
6. 确认所有 Harness 进程退出后再交给安装器。

**失败行为**：无法确认停稳时取消安装，保留已下载制品；不得在 Harness 仍写数据时强制覆盖 Runtime。

## 6. 数据迁移功能

### UPD-006：升级预检

预检条件：更新包签名有效、兼容 Manifest 完整、当前数据锁可获取、没有活动写入、可用磁盘建议大于数据目录的 2.5 倍。

若官方 Session 格式或 Runtime 无迁移能力，必须在切换前阻止升级，而不是安装后再提示用户。

### UPD-007：Copy-on-Upgrade

流程：

1. 对当前 Harness Home 获取独占锁。
2. 完成旧 Runtime flush 并记录源目录清单。
3. 将数据复制到 `staging/home-<target-version>`。
4. 校验文件数量、大小和 Hash；保留源目录只读。
5. 新 Runtime 只在 staging 副本上执行迁移或读取 Smoke。
6. 使用 Golden Session 检查 list/open/page/follow 和关键投影。
7. 全部成功后原子切换 `current` 指针或目录引用。
8. 保留升级前快照直到观察窗口结束。

**禁止事项**：禁止在当前活动 Home 上原地破坏性迁移；禁止部分复制完成后更新 current；禁止迁移失败后删除唯一副本。

### UPD-008：桌面偏好迁移

UI 设置、布局、草稿索引等采用独立 Schema Version 和逐版本纯迁移函数。迁移必须幂等，并在副本上执行；可重建缓存不迁移。

偏好迁移失败可回退到默认 UI 设置，但不得因此删除 Harness Home 或 Session。

## 7. 回滚功能

### UPD-009：二进制回滚

若新版本尚未写入新数据格式，启动验证失败时自动切回上一签名 App/Runtime 版本。目标 RTO 不超过 2 分钟。

### UPD-010：数据回滚

若新版本已经写入新格式：

- 旧 Runtime 禁止打开新 Home。
- 回滚切换到升级前只读快照的副本。
- 新 Home 必须完整保留，供之后只读恢复、导入或升级版本继续使用。
- 不得静默丢弃升级后新建的 Session；必须在操作前向用户解释数据分叉。

目标 Recovery Mode RTO 不超过 15 分钟。无法保证语义恢复时，应在 UPD-006 阶段阻止更新。

### UPD-011：崩溃点验证

在下载、复制、校验、迁移、切换 current、安装和首次启动验证的每一步注入进程崩溃、断电模拟、磁盘满和权限拒绝。

**DoD**：每个注入点之后至少有一个已签名应用版本和一份完整数据副本可启动；20 次完整升级/故障/回滚演练全部成功。

## 8. 平台发布顺序

| 平台 | 计划 | 特殊门禁 |
|---|---|---|
| Windows x64 | V1 首发 | Authenticode、Job Object、原生安装/更新 |
| macOS arm64 | V1 后续 | macOS 14+、Hardened Runtime、Notarize、Staple、Helper 签名 |
| Linux x64 | 后续 | glibc 2.28+、deb/rpm 仓库签名优先 |
| Linux arm64 | 后续 | 原生 Runner 与 Runtime 制品验证 |
| Windows ARM64 | 暂不支持 | 等待官方 Runtime |
| macOS Intel | 暂不支持 | 等待官方 Runtime或明确结束支持 |

## 9. 发布运行手册

每次发布必须保存：

- 功能追踪矩阵和已知限制。
- Commit、Lockfile、Release Manifest、Runtime Hash。
- 单元、合同、E2E、安全、性能、Soak 报告。
- SBOM、许可证、Provenance、签名验证结果。
- Clean Install、N-1 → N、Rollback、Uninstall 结果。
- 数据兼容范围和恢复操作。
- 发布 Owner、监控窗口和紧急回滚联系人。

自动暂停发布条件：确认的凭据泄漏、数据损坏、签名异常、启动失败率超过阈值、更新失败率超过阈值或 Crash-free 指标跌破门禁。

## 10. 模块验收清单

- [ ] Release Manifest 的所有字段由构建自动生成并在启动时校验。
- [ ] Runtime 不依赖用户系统 Node，且启动前验证签名与 Hash。
- [ ] Main、Preload、Bridge、Renderer 独立构建并通过依赖边界检查。
- [ ] 最终制品具有签名、SBOM、许可证和 Provenance。
- [ ] 更新渠道互相隔离且推广同一签名制品。
- [ ] A/B/C 三类更新拥有明确策略。
- [ ] 活动工作 Drain 完成前不会安装更新。
- [ ] Copy-on-Upgrade 不修改当前活动 Home。
- [ ] 旧 Runtime 无法打开新格式数据。
- [ ] Clean Install、升级、回滚和卸载均有真实安装包 E2E。
- [ ] 每个故障注入点都能恢复到完整应用和完整数据。

## 11. 开发顺序与依赖门禁

1. **发布身份**：先完成 BASE Release Set、PKG-001 和数据所有权登记；Manifest 无法由真实制品自动生成时，不开始自动更新。
2. **可重复构建**：完成 PKG-002～PKG-003、依赖边界、Fuses 和未签名制品；两个干净环境无法得到一致内容时，不接入签名。
3. **安装生命周期**：完成 PKG-004 和 Runtime/Bridge 全量停稳合同；应用无法证明 Sidecar 退出时，不允许安装器覆盖 Runtime。
4. **供应链**：完成 PKG-005、隔离签名、SBOM、许可证、Provenance 与最终制品复验；普通 CI 和 Fork PR 不得持有发布权限。
5. **更新控制面**：完成 UPD-001～UPD-005，先验证 A 类，再验证 B 类；下载、验证、Drain 任一步失败必须保持当前版本可运行。
6. **数据升级**：只有上游格式与迁移能力已经核验，才实现 UPD-006～UPD-008；未知格式按 C 类并默认阻断。
7. **回滚**：完成 UPD-009～UPD-011 和逐崩溃点测试；旧版本、旧数据和升级后新数据的保留语义必须分别验证。
8. **发布推广**：Clean Install、N-1→N、Rollback、Repair、Uninstall 全部在最终签名制品通过后，才允许 Internal→Beta→Stable 推广。

## 12. 模块完成定义

本模块只有同时满足以下条件才可完成：

1. PKG-001～PKG-005、UPD-001～UPD-011 均在追踪矩阵达到 `VERIFIED`，且 Evidence 绑定同一 Release Set。
2. 安装内容能反向核对源码 Commit、Lockfile、Harness tag/commit/hash、官方 Client、Compat、协议指纹、数据格式和构建环境。
3. 最终 EXE/DLL/Installer、更新 Manifest 与 Runtime 均通过签名和 Hash 校验，SBOM、许可证和 Provenance 完整。
4. Clean Install、保留数据重装、N-1→N、更新中断、迁移失败、二进制回滚、数据恢复和 Uninstall 在干净 Windows VM 通过。
5. 每个更新崩溃点都至少保留一个可启动签名版本和一份完整数据副本；任何旧 Runtime 都无法写入新格式 Home。
6. 发布、暂停、Kill Switch、恢复和回滚 Runbook 可由未参与开发的工程师按文档完成，不依赖删除用户数据。
