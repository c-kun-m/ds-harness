# 17：开发阶段、任务与里程碑

## 1. 使用方式

本文件是整个 UI 项目的执行主线。每次目标模式运行都应从这里选择尚未完成的最前置任务，并同时查阅该任务对应的模块文档和功能追踪矩阵。

硬规则：上一阶段退出门禁未通过，不进入下一阶段；可以并行实现同阶段互不依赖的任务，但不能用后续 UI 工作掩盖前置协议、状态或生命周期问题。

状态使用：`未开始`、`进行中`、`被阻塞`、`已实现待验收`、`已完成`。只有具有代码、测试和验收证据的项目才能标为已完成。

## 3. Phase 0：范围冻结与上游锁定

### 目标

把“要做什么、明确不做什么、依赖哪个官方版本、每项功能对应哪个官方能力”写成可审计合同。

### 前置条件

- 当前上游源码可读取。
- 产品目标确认为 Electron + Vue 自定义 UI，对接受管本机官方 Harness。

### 任务顺序

1. `P0-01`：建立 Must/Should/Later/Unsupported 功能清单。
2. `P0-02`：锁定 Harness tag、commit、官方 Client 包和 Runtime 构建目标。
3. `P0-03`：枚举官方 Remote 方法、事件、stream、错误和 transient interaction。
4. `P0-04`：建立 Release/Protocol/Data compatibility manifest 结构。
5. `P0-05`：确认所有官方 Client、Cordis、Controller、Conversation Projection 运行在 Utility。
6. `P0-06`：列出动态 React Client 依赖并决定禁用或替代。
7. `P0-07`：建立信任边界与初版威胁模型。
8. `P0-08`：确定 Windows x64 首发和其他平台支持状态。
9. `P0-09`：建立 ADR 索引和首批关键决策。

### 交付物

- `00-产品目标范围与完成定义.md`
- `01-技术基线与上游锁定.md`
- `02-总体架构与进程边界.md`
- `03-全量功能清单.md`
- `upstream.lock.json` 的 Schema 与生成任务设计
- 协议能力目录和风险登记

### 退出门禁

- 所有 Must 功能均能映射到官方能力或明确的桌面本地能力。
- 不存在未决定的 Client 运行位置和状态所有权。
- 外部远程 Host、任意第三方 Renderer JS 等非目标能力已明确排除。
- 每项 P0 风险都有验证任务和 Owner。

### 验收证据

功能矩阵评审记录、上游 commit 输出、依赖图、威胁模型和 ADR。

## 4. Phase 1：官方接入可行性验证

### 目标

在开发完整界面前，用发布形态证明官方 Harness 能被安全启动、认证、调用、投影、恢复和关闭。

### 任务顺序

1. `P1-01`：构建或取得 Windows x64 发布形态 Runtime，生成 Hash。
2. `P1-02`：建立隔离 Harness Home 和无真实 API Key 的测试夹具。
3. `P1-03`：实现最小 Supervisor，启动随机 loopback 端口。
4. `P1-04`：实现限长 Readiness Parser 和 Token canary 测试。
5. `P1-05`：Utility 完成 Token → Cookie 交换。
6. `P1-06`：跑通第一个官方 Unary RPC。
7. `P1-07`：跑通 `/api/remote.mux` 和多逻辑 Stream。
8. `P1-08`：在 Utility 创建官方 Client Context 和静态 Controller。
9. `P1-09`：跑通 Workspace list/create。
10. `P1-10`：跑通 Session list/create/prompt/follow/cancel/page。
11. `P1-11`：跑通 Approval、User Question 和 generation 失效。
12. `P1-12`：验证断线、重连、Gap Repair 和 Snapshot Sync Barrier。
13. `P1-13`：验证 Headless Conversation Projection，不加载 React。
14. `P1-14`：验证 stdin lifecycle 和 Windows Job Object 清理。
15. `P1-15`：生成 Golden Session fixture 和官方 Web 语义基线。

### 退出门禁

- 十五项 Spike 全部以自动化或可重放证据通过。
- 启动/关闭 100 次无孤儿进程和端口泄漏。
- Token、Cookie、API Key 未进入 stdout 日志、文件日志和 CI Artifact。
- 真实 Session 能稳定投影成 DTO，关键语义与官方 Web 一致。
- 若官方 Client 无法在 Utility 运行，停止后续开发并修订架构 ADR，不能把依赖临时塞进 Renderer。

## 5. Phase 2：工程骨架与公共合同

### 任务顺序

1. `P2-01`：创建 `apps/desktop` Main、Preload、Bridge、Renderer 入口。
2. `P2-02`：创建 `desktop-contracts` 与 UI Protocol Version。
3. `P2-03`：建立 request/reply/event/error Schema 和限额。
4. `P2-04`：建立 `harness-compat/v0_1_2` 唯一官方依赖边界。
5. `P2-05`：配置 TypeScript Project References、Lint 和依赖规则。
6. `P2-06`：配置开发/测试/生产环境并做启动校验。
7. `P2-07`：建立 test-support、Fake Host 和 fixture 目录。
8. `P2-08`：建立 PR CI 与 frozen lockfile 安装。
9. `P2-09`：建立版本 Manifest 生成和构建产物 Hash。

### 退出门禁

- 干净环境一条命令完成安装、typecheck、test 和 build。
- Renderer 导入 Node、Electron 或官方 Harness 包时 CI 失败。
- 所有跨进程 Payload 具有运行时 Schema。
- 可打包打开一个无业务、但安全配置完整的本地窗口。

### 任务顺序

1. `P3-01`：单实例、App Paths、异常退出标记和恢复入口。
2. `P3-02`：注册只读 `app://desktop/` 与 CSP。
3. `P3-03`：创建 sandbox BrowserWindow 和导航/权限拦截。
4. `P3-04`：实现 Preload 固定 API 与 sender 校验。
5. `P3-05`：实现 Runtime Manifest、平台选择和完整性校验。
6. `P3-06`：完成 Supervisor 全状态机和状态日志。
7. `P3-07`：完成 Home 独占锁、启动超时和 Crash Loop Fuse。
8. `P3-08`：完成 stdin drain、强制退出和 Windows Job Object。
9. `P3-09`：实现 Boot、Failure、Recovery 基础页面。

### 退出门禁

- 500 次自动启停无孤儿进程。
- 篡改 Runtime、伪造 Readiness、异常 Host/Port 均拒绝启动。
- Renderer 不能访问 Node、网络和原始 IPC。

## 7. Phase 4：Bridge 与官方 Client

### 任务顺序

1. `P4-01`：Utility Process 启动和双 MessagePort 生命周期。
2. `P4-02`：内存 CookieJar、authority 校验和 direct/no-proxy 传输。
3. `P4-03`：Unary deadline、Abort、错误映射和容量边界。
4. `P4-04`：Mux Stream open/item/end/error/cancel。
5. `P4-05`：官方 Connection、Gateway、Remotes 和 Controller 组合。
6. `P4-06`：Connection Generation、重连退避和 Sync Barrier。
7. `P4-07`：Credit-based backpressure 与后台 Session 合批。
8. `P4-08`：mutating command 的 `OUTCOME_UNKNOWN` 语义。
9. `P4-09`：Bridge 崩溃重建和全量 Resync。
10. `P4-10`：协议指纹检查和 Capability Snapshot。

### 退出门禁

- Unary、Stream、Cancel、Reconnect、Resync 全部通过 Fake 与真实 Host 测试。
- 1,000 次断线/重连无跨 generation 污染。
- 事件风暴和慢 Renderer 不造成无界内存。
- Renderer、Preload 和 Main 日志均不能取得 Cookie。

- P0/P1 缺陷为零。
- 回滚值班、支持文档和恢复手册可执行。

## 15. 每个任务的固定工作流

1. 从功能追踪矩阵选取最前置的未完成功能 ID。
2. 阅读对应模块文档的接口、状态机、错误、安全和测试要求。
3. 检查当前源码和官方固定版本，确认假设仍成立。
4. 在计划中标记一个 in-progress 任务。
5. 先补合同/测试夹具，再实现最小完整纵向切片。
6. 运行该模块要求的单元、合同、集成、安全或性能测试。
7. 回填追踪矩阵中的代码位置、测试位置和验收证据。
8. 检查未提交的用户改动，不覆盖无关文件。
9. 形成一个主题清晰的 Git commit，禁止 `--no-verify`。
10. 只有证据覆盖全部 DoD 后才把状态改为已完成。
