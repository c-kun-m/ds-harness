# 18：功能追踪矩阵

## 1. 文档目标

本文件把产品范围、模块规格、开发阶段、代码归属、测试类型和发布证据连接成一条可审计链路。它解决的不是“有哪些想法”，而是后续每一次目标模式开发如何确定下一件事、如何证明做完、如何避免遗漏。

当前基线包含 **280 个功能 ID**：P0 134 项、P1 125 项、P2 21 项。当前只完成规划文档，尚未开始桌面端实现，所以所有功能的实现状态均为 `PROPOSED`；文档存在不能被记为 `IMPLEMENTED`。

三个真源的职责不可互换：

| 真源 | 负责回答 | 不负责回答 |
|---|---|---|
| `03-全量功能清单.md` | 功能是否在范围内、优先级、用户行为和验收摘要 | 逐步实现细节 |
| `05`～`16` 模块文档 | 接口、状态机、实现步骤、限额、故障、安全、测试和 DoD | 实时完成状态 |
| 本文件及 `evidence/<ID>/manifest.json` | 阶段、责任位置、当前状态和证据闭环 | 改写产品范围或模块合同 |

任何一处发生冲突时，先停止编码：范围问题回到 `03`，实现问题回到责任模块文档，完成状态以可验证 Evidence 为准。

## 2. 追踪规则

1. 一个生产改动必须至少归属一个功能 ID；基础重构也必须归属 `ARCH`、`ENG`、`SEC`、`TEST` 或其他真实目标。
2. 一个功能可以拆成多个提交，但一个提交只包含一个可独立回退的主题，并在标题或正文写明功能 ID。
3. 跨模块纵向切片允许同时选择多个 ID，但必须逐项保存证据，不能用一条 E2E 结果笼统覆盖整组功能。
4. 任何 P0 未达到阶段门禁时，依赖它的 P1/P2 不得进入 `VERIFIED`。
5. `IMPLEMENTED` 仅表示代码存在；测试、人工验收、性能/安全门禁和文档未齐时不得进入 `VERIFIED`。
6. 没有 Evidence Manifest 的功能一律按 `PROPOSED` 处理；禁止根据分支名、页面截图或口头说明推断完成。
7. 删除或推迟范围必须保留原 ID，记录 ADR、替代项、影响阶段和批准人，不得直接从总账删行。
8. 每次开始和结束目标模式运行，都必须执行 `node UI开发/scripts/verify-docs.mjs`。

## 5. 单功能 Evidence Manifest

当某个功能第一次进入 `IN_PROGRESS` 时创建：

```text
UI开发/evidence/<FEATURE-ID>/manifest.json
```

建议 Schema：

```json
{
  "featureId": "BRG-004",
  "status": "IN_PROGRESS",
  "owner": "desktop-platform",
  "releaseSetId": "pending",
  "moduleSpec": "UI开发/07-Bridge传输与官方客户端兼容层.md",
  "implementation": [],
  "tests": [],
  "commands": [],
  "artifacts": [],
  "commits": [],
  "securityReview": null,
  "performanceReview": null,
  "manualAcceptance": null,
  "blockedBy": [],
  "knownLimitations": [],
  "updatedAt": "ISO-8601"
}
```

字段规则：

| 字段 | 强制时点 | 规则 |
|---|---|---|
| `featureId` | 创建时 | 必须存在于 `03`，目录名与值完全一致 |
| `status` | 始终 | 只能使用规定状态；状态倒退必须附原因 |
| `releaseSetId` | `VERIFIED` 前 | 必须指向已核验的 App/Runtime/Client/Compat 组合 |
| `implementation` | `IMPLEMENTED` 前 | 使用仓库相对路径和符号名，不使用模糊目录描述 |
| `tests` | `VERIFIED` 前 | 列出测试文件与具体用例/项目，不只写“已测试” |
| `commands` | `VERIFIED` 前 | 记录可重放命令、退出码和产物位置；不能仅贴终端截图 |
| `artifacts` | 按模块 | 性能、视觉、差分、安全、签名或迁移报告的路径/Hash |
| `commits` | 每次提交后 | 只记录已存在 commit；工作树内容不算证据 |
| `securityReview` | 涉及信任边界时 | 记录威胁项、审查结论和残余风险 |
| `performanceReview` | 涉及流、列表、Worker 时 | 同时记录绝对预算和相对基线 |
| `manualAcceptance` | `VERIFIED` 前 | 记录环境、步骤、结果和验收人/自动代理身份 |
| `blockedBy` | 阻塞时 | 只引用功能 ID、Risk ID 或 ADR ID，不写无法追踪的描述 |

Evidence 不得包含 Token、Cookie、API Key、Prompt、模型响应正文、用户文件内容或可识别的绝对私人路径。

## 6. 状态转换门禁

| 目标状态 | 必须满足 | 不允许 |
|---|---|---|
| `PROPOSED` | 已进入 03、责任文档和本矩阵 | 以此状态开始生产实现 |
| `APPROVED` | 范围、上游依据、前置依赖、风险和 DoR 已审核 | 仍有未决 P0 架构选择 |
| `IN_PROGRESS` | 计划只有一个当前步骤；Evidence 已创建；工作树已检查 | 覆盖用户无关改动或跳过前置门禁 |
| `IMPLEMENTED` | 代码、Schema、错误路径、资源释放和基础测试存在 | 以页面可见或 happy path 代替完整实现 |
| `VERIFIED` | 模块 DoD、所需自动测试、手工验收、安全/性能门禁与文档齐全 | Flaky 重跑后把失败当成功；缺失真实 Harness 合同测试 |
| `RELEASED` | 同一签名制品通过 RC、Release Manifest 可追溯、发布审批完成 | 重建制品后沿用旧证据 |
| `BLOCKED` | 明确阻断原因、复现、Owner、下一解除条件 | 用“复杂”“待观察”掩盖未知状态 |
| `REMOVED` | 已批准范围变更、替代项和 Release Notes | 删除 ID 或抹去历史证据 |

## 7. 后续目标模式的标准执行流程

每次开始实现时严格执行以下顺序：

1. 读取本文件、`17-开发阶段任务与里程碑.md` 和当前阶段责任文档。
2. 运行文档验证器，确认基线没有缺号、断链或责任漂移。
3. 读取 Git 状态，区分用户已有改动；不得把无关改动纳入本次提交。
4. 从当前阶段选择最前置的一个功能 ID；只有同一纵向切片不可分割时才同时选择多个。
5. 检查该 ID 在 `03` 的用户行为/优先级，以及模块文档的接口、状态机、限额、故障、安全、测试和 DoD。
6. 校验官方固定版本的真实源码和运行行为；发现文档假设漂移先更新 BASE/ADR/模块合同。
7. 创建 Evidence Manifest，将状态改为 `IN_PROGRESS`，并列出本次精确文件和测试计划。
8. 先实现合同、测试夹具或失败路径，再完成最小可用纵向切片。
9. 运行与风险成比例的单元、属性、合同、集成、E2E、安全、性能测试；记录命令和产物。
10. 对照该功能所有 DoD 逐项审计，更新实现路径、测试、限制、Review 和状态。
11. 运行文档验证器、类型检查、模块测试和 `git diff --check`。
12. 只暂存本次功能相关文件，使用正常 Hook 创建一个主题清晰的 Git commit，禁止 `--no-verify`。
13. 提交后核验工作树和 Evidence 中的 commit；仍有未完成 DoD 时保持 `IMPLEMENTED`，不得写 `VERIFIED`。
14. 阶段内所有阻塞功能完成后，再执行 `17` 的阶段退出门禁；不得按日期自动进入下一阶段。

## 8. 纵向旅程覆盖

单模块测试不能代替用户旅程。以下旅程必须把所列功能的 Evidence 串联到同一个最终签名制品：

| 旅程 | 最低覆盖 | 关键失败注入 | 最终证据 |
|---|---|---|---|
| 首次启动到首条回复 | BASE、ELM、HRS、BRG、SES、CP、VUE、CONV、COMP | Runtime 缺失、认证失败、流中断 | packaged E2E + support-code trace |
| 重启恢复长会话 | HRS、BRG、SES、CP、VUE、CONV、REC、PERF | Renderer/Bridge/Harness 分别崩溃 | replay diff + heap/resource report |
| Approval / Question | BRG、CP、INT、CONV、A11Y、SEC | 过期、重复提交、跨 generation | state-machine property + keyboard E2E |
| Tool / Diff / Subagent / Goal | CP、TOOL、SUB、GOAL、SEC、PERF | 畸形 payload、循环树、超大输出 | malicious corpus + worker benchmark + E2E |
| 设置与凭据 | SET、CRED、HRS、SEC、OBS | Keychain 失败、重启失败、Secret canary | platform integration + zero-leak scan |
| 更新与回滚 | BASE、ELM、HRS、REC、PKG、UPD、TEST | 下载截断、断电、磁盘满、迁移失败 | signed N-1→N→rollback report |
| 完整可访问体验 | DS、GSAP、I18N、A11Y、VUE、CONV、COMP | reduced-motion、200% zoom、伪语言 | visual + axe + keyboard + NVDA report |

## 9. 阶段和发布覆盖算法

阶段退出检查：

```text
phaseExitAllowed =
  requiredFeatureIds.every(status >= VERIFIED)
  && requiredEvidenceFamilies.every(result == PASS)
  && openP0Risks == 0
  && forbiddenDependencyEdges == 0
  && secretCanaryMatches == 0
```

GA 检查：

```text
gaAllowed =
  all(P0 | P1 | P2).status >= VERIFIED
  && releaseCandidate.isSameSignedArtifactAsPromotedBuild
  && releaseManifest.matchesInstalledFiles
  && securityGate == PASS
  && performanceGate == PASS
  && migrationAndRollbackGate == PASS
  && documentationCoverage == 100%
```

任何例外必须是有截止时间、Owner、影响分析和回滚方案的批准记录；不能把例外直接改写成测试通过。
