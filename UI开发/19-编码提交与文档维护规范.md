# 19：编码、提交与文档维护规范

## 1. 文档目标

本文件规定如何把 `UI开发` 中的规格持续转化为代码，同时避免功能遗漏、边界漂移、测试欠账和无法回溯的大提交。

开发人员和自动化 Agent 都必须遵守。任何“先临时打通、以后再补”的实现都必须显式登记为债务、限定期限，并且不能绕过当前阶段的退出门禁。

## 2. 单一真源

| 信息 | 真源 |
|---|---|
| 产品范围、Must/Later/Unsupported | `00-产品目标范围与完成定义.md`、`03-全量功能清单.md` |
| 技术版本和上游身份 | `01-技术基线与上游锁定.md`、生成的 `upstream.lock.json` |
| 进程与信任边界 | `02-总体架构与进程边界.md` |
| 模块接口和实现要求 | 对应编号模块文档 |
| 开发先后顺序 | `17-开发阶段任务与里程碑.md` |
| 功能完成状态和证据 | `18-功能追踪矩阵.md` |
| 安全、性能和发布门禁 | `14`、`15`、`16` 文档 |
| 未决设计选择 | `20-风险登记与ADR索引.md` |

同一规则不得在多个文件产生互相冲突的版本。重复摘要必须链接回真源；修改真源后同步检查所有引用。

## 3. 功能 ID 与状态

功能 ID 前缀：

```text
PRD BASE ARCH ENG ELM HRS BRG
WS SES CP VUE CONV COMP TOOL INT SUB GOAL
SET CRED DS GSAP I18N A11Y
SEC OBS REC TEST PERF PKG UPD
DOC
```

状态：

```text
PROPOSED → APPROVED → IN_PROGRESS → IMPLEMENTED → VERIFIED → RELEASED
                  ↘ BLOCKED
                  ↘ REMOVED
```

`VERIFIED` 必须同时具有：代码位置、测试位置、验收命令或制品、对应 commit。只有 PR、代码片段、计划或人工口头确认不能证明完成。明确不支持或移出范围的功能使用 `REMOVED`，同时保留原 ID、原因、替代项和批准记录。

## 4. 模块文档固定模板

新模块或拆分模块时，文档必须包含以下章节：

1. 模块目标。
2. 范围和非范围。
3. 上游依据与依赖。
4. 建议目录和依赖方向。
5. 公共接口、DTO、Command、Event、Patch。
6. 状态机和不变量。
7. 完整功能列表及功能 ID。
8. 每项功能的用户行为。
9. 每项功能的实现步骤。
10. 输入校验和容量上限。
11. 错误、取消、断线和恢复行为。
12. 安全与隐私要求。
13. 单元、合同、集成、E2E、性能测试。
14. 开发任务顺序。
15. Definition of Done。
16. 验收清单。

模块文档中不得只写“实现列表”“调用 API”“处理异常”等不可执行描述，必须点名数据、状态和失败行为。

## 5. Definition of Ready

一个功能可以进入编码前必须满足：

- [ ] 已分配唯一功能 ID。
- [ ] 用户可观察行为已定义。
- [ ] 范围和明确非范围已定义。
- [ ] 所属进程和权限边界已确定。
- [ ] 官方 Remote/Controller 或本地能力来源已核验。
- [ ] 输入、输出和运行时 Schema 已设计。
- [ ] 状态机、不变量、幂等性和取消语义已明确。
- [ ] 空态、加载、成功、失败、断线和恢复行为已明确。
- [ ] 容量、超时和资源释放上限已明确。
- [ ] 安全和隐私影响已评估。
- [ ] 测试层级、fixture 和验收命令已确定。
- [ ] 前置功能均已完成，或存在经批准的测试替身。

缺少任意一项时应继续完善规格，不直接写不可验证的业务代码。

## 6. Definition of Done

一个功能只有满足以下全部条件才能完成：

- [ ] 正常、空态、加载、失败、取消、断线和恢复路径均已实现。
- [ ] 所有输入输出经过运行时 Schema 校验。
- [ ] 队列、文本、数组、文件、帧、递归和时间均有上限。
- [ ] 未知数据有安全 fallback，required unknown 不被静默吞掉。
- [ ] 单元和对应的合同/集成/E2E 测试通过。
- [ ] 安全、无障碍、性能要求按功能影响完成验证。
- [ ] 重复进入、卸载和重连后无 Listener、Timer、Worker、Socket、Tween 泄漏。
- [ ] 日志仅包含批准字段并通过 Secret Canary。
- [ ] 文档和功能追踪矩阵已同步。
- [ ] 代码通过 format、lint、typecheck、test 和 build。
- [ ] 已形成一个主题清晰且通过正常 Hook 的 Git commit。

## 7. 编码边界

### 7.1 依赖规则

- `apps/desktop` 不得依赖当前实验性的 `packages/kernel`。
- 只有 `packages/harness-compat/<version>` 可以导入 `@deepseek-ai/dsh-*` 和 Cordis。
- Renderer 只能依赖 Desktop DTO、Vue 适配、设计系统和纯展示模块。
- Main 不得解析 Conversation/Tool 的业务语义。
- Tool Presenter 不得直接访问 Preload、Bridge、Transport 或文件系统。
- GSAP 不得读取或写入 Harness 状态，不得把 Timeline 放进 Pinia。
- 测试替身不得进入生产依赖图。

### 7.2 类型与协议

- 禁止在跨进程合同中使用 `any`、Function、Class、Error、Map、Set 和循环结构。
- 未知输入首先是 `unknown`，通过 Schema 后才进入领域代码。
- Command、Event、Patch 必须是封闭联合，新增类型需更新完整性测试。
- 时间、ID、序号、revision 和 generation 的单位与语义必须在类型名或注释中明确。
- 非幂等写操作必须具有 clientCommandId，并定义 `OUTCOME_UNKNOWN`。

### 7.3 状态所有权

- Harness 是 Session、Workspace、Queue、Turn 和 Tool 执行的真源。
- Official Controller/Projector 在 Utility 维护领域投影。
- Renderer 只维护 DTO View、路由、面板、草稿和偏好。
- 不允许在 Pinia 再写一套 Session Reducer。
- Snapshot/Patch revision 不连续时必须 Resync，不能猜测补齐。

### 7.4 安全默认值

- 所有模型内容、工具输出、文件内容、URL 和 IPC Payload 均不可信。
- Renderer 无 Node、网络、原始 IPC 和明文 Secret。
- 外链、文件、剪贴板、通知、更新均通过最小原生 Capability。
- 未识别 Tool 使用 Generic Card；未验证插件不得执行 Renderer JavaScript。

## 8. 开发任务模板

每个实现任务使用以下模板：

```text
任务 ID：P?-?? / 功能 ID
目标：用户最终能观察到什么
非目标：本任务明确不处理什么
前置：已完成的功能和可用 fixture
源码依据：官方文件/接口/当前实现
涉及进程：Main / Preload / Bridge / Renderer / Harness
合同变化：Command / Event / DTO / Patch / Error
状态变化：状态机与不变量
实现步骤：按可验证顺序列出
失败与恢复：超时、取消、断线、崩溃、结果未知
安全与限额：Schema、权限、字节、并发、时间
测试：单元 / 合同 / 集成 / E2E / 安全 / 性能
验收命令：可以重复运行的命令或制品步骤
文档回填：模块文档与追踪矩阵
提交：主题和预期 commit message
```

## 9. Git 提交规则

- 每完成一个可独立回退的代码或文档变更立即提交。
- 一个提交只解决一个主题，不混入无关格式化、重构或用户改动。
- 提交前检查 `git diff`、`git diff --check`、相关测试和仓库状态。
- 禁止 `git commit --no-verify`。
- 禁止覆盖、重置或顺带提交无法确认来源的工作树修改。
- 机械生成文件必须与生成源放在同一个提交，并验证可重复生成。
- 修复评审问题时，如属于同一未发布任务可以独立修复提交；不得改写用户历史，除非用户明确要求。

建议消息前缀：

```text
docs(ui): ...
chore(desktop): ...
feat(supervisor): ...
feat(bridge): ...
feat(session): ...
feat(renderer): ...
test(desktop): ...
fix(...): ...
```

## 10. 功能完整性审计

每个阶段结束时执行：

1. 从 `03-全量功能清单.md` 枚举该阶段要求的 P0/P1/P2 ID。
2. 在 `18-功能追踪矩阵.md` 检查模块、阶段、代码、测试和证据字段。
3. 在模块文档检查正常、失败、取消、恢复、安全和性能要求。
4. 搜索生产代码的 TODO/FIXME、临时 `any`、私有上游路径和通用 IPC。
5. 检查按钮、菜单、命令和 Capability 是否存在无后端或无 UI 的孤儿功能。
6. 用 Golden Fixture 和真实 Harness 运行阶段 E2E。
7. 将缺口作为功能 ID 或缺陷登记，不能仅记录在聊天或个人笔记中。
8. 所有退出门禁证据齐全后，才能开始下一阶段。

矩阵完整性至少验证：

- 清单中的每个 ID 在矩阵恰好出现一次。
- 模块文档中的每个 ID 已在清单登记。
- 每个 Must ID 有测试类型和验收证据要求。
- 每个已完成 ID 有代码位置、测试位置和 commit。
- Unsupported ID 有用户界面策略，不出现无响应入口。

## 11. 文档变更流程

- 功能范围改变：先改 00/03，再改模块、阶段和矩阵。
- 架构边界改变：先新增或更新 ADR，再改 02、相关模块和测试。
- 官方版本升级：先生成协议/Schema Diff，再创建新的 compat 文档和目录。
- 性能预算改变：附专用 Runner 的 Trace、Heap 或基准证据，并通过 ADR 审批。
- 安全例外：必须有 Owner、缓解措施、到期时间；Secret/Data 类问题不得例外发布。
- 文档删除：先证明没有功能 ID、链接、任务或测试引用它。

## 12. 每次目标模式运行的结束审计

每次运行结束前必须报告：

1. 本轮推进的功能 ID。
2. 修改的文件和核心行为。
3. 执行的测试与结果。
4. 未完成项和真实阻塞。
5. 工作树中保留的用户既有改动。
6. 本轮提交 Hash。
7. 下一轮最前置任务。

如果目标尚未全部完成，保持目标为 active；不能因为本轮完成一个子模块就把整个工业级 UI 目标标记为完成。
