# 03 具体开发实战：完整插件内核

这份文件是你实际写代码时使用的任务手册。它不提供最终实现代码；每一批只告诉你三个功能要解决什么、必须表现成什么样、怎样测试。你先写，写完后再让我审查，我们再根据失败证据讨论实现。

完整原理课在 [`开发文档/03-插件内核完整课程/`](../开发文档/03-插件内核完整课程/README.md)。这里不重复长篇源码解释。

## 0. 先确认当前代码的定位

项目目前已有一个简单 `EffectStack`。无论它是否已经通过现有测试，都只算 K01 热身：它可以证明“逆序调用”和“重复 dispose 不重复副作用”，不能证明 Cordis 的完整 Effect/Fiber。

后续不要继续把所有功能塞进 `EffectStack`。建议保留它作为基础练习，正式模型另设 Fiber、EffectRecord/Runner、Registry、Context、Reflect、Events 和 Scope 边界。具体文件名由你决定。

## 1. 你每次怎么做

每一批有三项任务。顺序固定：

1. 先读“为什么”；
2. 用自己的话写出公共行为；
3. 先补失败测试；
4. 再写实现；
5. 运行本批相关测试、typecheck、build；
6. 把结果告诉我，我先审查，不会自动给下一批答案；
7. 审查通过后做一次只包含本批的 commit。

遇到不会的地方，先问“这个状态下系统应该发生什么”，不要先问“这一行代码怎么写”。

## 2. Build 后多出来的文件是什么

TypeScript package 常见构建产物是：

```text
packages/kernel/
  dist/
    *.js       运行时 JavaScript
    *.d.ts     给其他 TypeScript 包使用的类型声明
    *.js.map   JavaScript 到 TypeScript 的调试映射
    *.d.ts.map 类型声明到源文件的导航映射（若启用）
  tsconfig.build.tsbuildinfo  增量编译缓存（若启用）
```

它们不是你要继续手改的源码。源码只改 `src/` 和 `tests/`；构建产物由编译器重建。是否提交由项目 `.gitignore` 和发布策略决定。每次不确定“多了什么”，用：

```powershell
git status --short
git status --ignored --short
```

第一条看未忽略变化，第二条也显示被忽略的构建产物。不要为了干净随便删除不认识的目录；先确认它是否由 build 生成。

## 3. 总体文件边界建议

这不是强制目录答案，只是职责边界：

```text
packages/kernel/src/
  disposable.*      精确、幂等的基础清理集合
  errors.*          稳定错误和校验问题
  fiber.*           状态、epoch、加载/卸载惯性
  effect.*          多形态 Effect 和清理事务
  registry.*        插件定义与运行实例索引
  context.*         root/child Context
  reflect.*         Service 代理、provide/inject/isolation
  events.*          多种分发模式
  loader.*          配置组合和 HMR

packages/scope/src/
  index.*           Scope、tag、parent、target
  store.*           Named/Anonymous/ScopedLayers
  invariant.*       作用域不变量
```

如果你采用其他结构，只要能清楚回答“哪个模块拥有状态和 disposer”即可。

# 批次 A：基础资源身份（K01）

## A1：有序清理集合

### 为什么

数组支持逆序，但提前删除通常要 O(n)，且容易按 callback/name 误删。你需要同时保留插入顺序和精确身份。

### 你要实现的功能

- 添加一条同步或异步 disposer；
- 返回与这一条记录绑定的撤销能力；
- owner 能原子取出当前全部记录的逆序快照；
- 已提前撤销的记录不再出现在 owner 清理中。

### 必测

- 三条记录按 3、2、1；
- 删除中间项后只剩 3、1；
- 两个相同 callback 仍是两条不同记录；
- 空集合清理。

## A2：幂等但可等待的 disposer

### 为什么

“第二次调用直接 return”会让第二个调用者在第一次异步清理仍运行时提前以为已经完成。

### 你要实现的功能

- 第一次调用启动清理；
- 并发或后续调用不重复副作用；
- 所有调用者只在同一个清理事务结束后结算；
- 拒绝也被所有等待者观察。

### 必测

- 两次同步调用，计数为 1；
- 两次并发调用慢 Promise，二者都不能提前结束；
- Promise 拒绝没有未处理 rejection。

## A3：旧句柄不能误删新记录

### 为什么

HMR 或服务替换后，旧实例的迟到 disposer 可能运行。如果撤销按名称查找，它会删除新实例。

### 你要实现的功能

- 注册 A，取得 undo-A；
- A 正常移除；
- 同名/同 callback 注册 B；
- 再调用 undo-A，B 必须仍存在。

### 本批完成信号

A1–A3 的测试使用公共 API，`EffectStack` 仍保持小而明确。把本批结论写入 `packages/kernel/PARITY.md`。

# 批次 B：错误与 Fiber 状态（K02–K03）

## B1：稳定内核错误

### 为什么

后面会出现配置、状态、依赖、用户回调和清理错误。调用方不能靠中文 message 猜类别。

### 你要实现的功能

- 稳定 code；
- phase；
- 相关 identity；
- cause；
- 安全的日志/协议 record。

### 必测

- 包装普通 Error 后 cause 保留；
- 重复包装不丢原 code；
- 序列化不含函数、秘密或完整堆栈。

## B2：Fiber 封闭状态机

### 为什么

`active: boolean` 无法表达加载失败和正在卸载。

### 你要实现的功能

- PENDING、LOADING、ACTIVE、FAILED、UNLOADING、DISPOSED；
- 只有合法转移可以发生；
- 状态 observer 收到 old/new/id；
- observer 抛错不回滚已提交状态。

### 必测

- 正常加载；
- 加载失败；
- ACTIVE 卸载；
- 所有非法转移；
- observer 内重入卸载。

## B3：重复 dispose 与停稳 Promise

### 为什么

状态改成 DISPOSED 不等于异步工作已经停下。

### 你要实现的功能

- 首次 dispose 关闭新工作；
- 后续 dispose 加入同一事务；
- Promise 只在全部已知清理结束后兑现；
- DISPOSED 后不复活。

### 本批完成信号

状态图与代码相符；并发 dispose 只产生一次状态序列；测试没有 sleep。

# 批次 C：真正的 EffectRunner（K04）

## C1：先登记 owner，再运行 setup

### 为什么

setup 内可能同步触发 Fiber 卸载。先运行 setup 会留下 owner 找不到的半成品。

### 你要实现的功能

- 检查 Fiber 可接纳；
- 创建 Effect record；
- 先登记 owner wrapper；
- 再调用用户 setup；
- setup 内重入卸载最终无泄漏。

## C2：支持全部返回形态

### 你要实现的功能

- void/null；
- 单 disposer；
- iterable disposers；
- promise disposer；
- async iterable disposers；
- 无效返回值明确失败。

### 必测

每种形态正常一次；iterable 逆序；无效值在失败后 owner 无残留。

## C3：同步/异步失败回滚

### 为什么

setup 可能已登记一部分资源后失败。

### 你要实现的功能

- 同步 throw 回滚已收集项；
- Promise reject 同样回滚；
- 主错误保留；
- 清理失败被聚合但不阻断剩余清理。

### 本批完成信号

setup 重入、异步拒绝、无效返回和清理失败都有确定性测试，无 Effect record 残留。

# 批次 D：并发、重入、停稳（K05）

## D1：一个 Effect 内逆序串行

同一 Effect 的 C/B/A 清理必须一个完成后再执行下一个；C 失败也要继续 B/A。

## D2：Sibling Effect 并发清理

Fiber 卸载时先关闭准入，再逆序取得 sibling Effect；多个 sibling 的清理可以同时启动，但 Fiber 要等待全部结算。

必测：让两个 sibling 都停在 barrier，证明它们同时已启动，而不是第一个完成后第二个才启动。

## D3：加入已经运行的清理

公开 disposer 先启动后，Fiber unload 仍要等待它；反向交错也不能重复清理。实现 cleanup inertia 或等价机制。

### 本批完成信号

disposer 内重入 `fiber.dispose()` 不死锁；dispose 兑现后 active effects、pending setup 和 cleanup inertia 都为空。

---

# 批次 E：父子插件树（K06）

## E1：父拥有子 disposer

父创建 child 时，在 child 对外发布之前先登记 child raw disposer。

## E2：创建/发布失败事务回滚

分别注入：child setup 失败、registry publish 失败、发布 observer 失败。任何场景都不能留下 tree 节点、Effect 或 listener。

## E3：级联与竞争释放

parent dispose 必须等待 child/grandchild；child 自 dispose 只移除自己；parent/child 同时 dispose 每项一次。

### 本批完成信号

三层插件树能正常创建和级联卸载；发布 observer 内重入 parent dispose 仍无孤儿。

---

# 批次 F：Plugin Registry（K07）

## F1：插件形态解析

支持函数、class/constructor、`{ apply }` 对象；非法形态在副作用前失败。不要只用 `typeof fn === 'function'` 假设所有函数都相同。

## F2：定义与实例分离

同一 plugin definition 可以有多个 Fiber；每个实例有独立 uid/config/handle；RuntimeRecord 只负责索引。

## F3：删除和旧句柄保护

删除 definition 会阻止新实例并释放现有实例；与 start 竞争时要么完整发布，要么完整回滚；旧 handle 不影响新世代。

### 本批完成信号

能解释 definition、record、fiber、handle 各自职责，Registry 不成为第二个生命周期 owner。

---

# 批次 G：Context 与 Service（K08–K09）

## G1：Root/Child Context

实现原型式 extend：子读父、父不读子；子注册归子 owner；disposed Context 拒绝新注册。

## G2：Service proxy、isolate、intercept

服务方法解构后调用仍保留正确 receiver 和 caller Context；isolate 只影响指定服务；intercept 按 root→nearest 合并。

## G3：Required 依赖消失与恢复

Provider 出现前 consumer 不运行；出现后加载；消失时 consumer 先卸载且清理窗口可访问 provider；provider 恢复后 consumer 新 epoch 重载。

### 本批完成信号

未声明服务访问被拒绝；两个 isolation 各自解析；required 链级联停稳无死锁。

---

# 批次 H：完整事件系统（K10）

## H1：Listener 注册维度

完成 on/once/prepend/filter/global 和精确 disposer。once 必须在调用 callback 前先撤销，以抵御重入 dispatch。

## H2：五种分发

分别实现 emit、parallel、serial、bail、waterfall，不用一个函数加很多布尔参数伪装。

## H3：错误和 bail 边界

parallel 等待全部并聚合错误；serial/bail 中 null/false/undefined 继续，0/空字符串/对象短路；waterfall 重复 next 稳定拒绝。

### 本批完成信号

每个生产事件都写明采用哪种 mode 和理由；async observer 不会制造未处理 rejection。

---

# 批次 I：配置、更新和诊断（K11）

## I1：同步配置校验

在 apply 前校验；多 issue 保留 path；异步 schema 结果明确拒绝；解析配置不受调用方后续修改。

## I2：Epoch 与 stale load

epoch 包含 required provider 世代和配置修订；加载等待期间 epoch 改变，旧 apply 不能发布 ACTIVE。

## I3：Update/Restart/Diagnostic

update 经过 waterfall 并返回权威结果；restart 复用完全卸载；并发 update 按明确队列策略；只读诊断包含状态/epoch/依赖/effect label/最近错误。

### 本批完成信号

并发 update A/B 和 stale load 的测试由 barrier 控制；诊断不泄露 disposer 或敏感配置。

---

# 批次 J：Loader 与 HMR（K12）

## J1：声明式条目和导出规范化

条目有稳定 id，不以数组位置做身份；模块不存在、非法导出、default/named 冲突都能定位。

## J2：HMR staging 与失败保留

新模块先加载、校验并尽可能 staging；失败不破坏旧实例；成功切换时只一个权威世代可见。

## J3：Watcher burst 与 Loader 停稳

用 fake watcher 触发 A/B/C burst，最终只发布 C 且事务不交错；Loader dispose 先停止新事件，再排空 import/update 和实例清理。

### 本批完成信号

明确记录你的 HMR 是否零停机、有哪些切换窗口、哪些副作用要求进程重启。

# 批次 K：DSH Scope（K13）

## K1：Scope、父链和停稳

创建带 backing Fiber 的 Scope；parent 只能由精确 binding 改绑；拒绝环；dispose 等 Fiber 和 inertia。

## K2：Scope 事件方向

child 事件可被 ancestor 观察，ancestor 不向 descendant 下泄；opaque target 不泄露 scope key；base filter 与 scope filter 组合。

## K3：ScopedLayers

完成 Named/Anonymous/ScopedLayers：只读不建层、global→far→near→exact 合并、undo 精确、notify 失败回滚 action、空 layer 回收。

### 本批完成信号

用工具、提示词、事件监听器各做一个 scoped 注册；释放 child 后 parent/global 仍在，child 所有内容消失。
