# 目标范围与版本路线

## 产品目标

实现一个独立的本体约束 Agent Runtime。它接收自然语言目标，使用模型处理歧义和非结构化信息，但只有本体策略允许的动作才会成为候选工具；工具执行前再次校验前置条件，执行结果写回事实状态，并把全部决策和副作用记录到可恢复的会话日志。

## MVP 成功标准

- 单个 DeepSeek 模型完成多 Step 工具调用循环。
- 单会话支持 follow-up、steer、inject 和 cancel。
- 工具具备输入校验、超时、审批、Guard、并发分类和有序结果提交。
- 会话事件能持久化、重放、恢复，并能识别崩溃时未确定的工具结果。
- 本体版本、实体、关系、事实、动作、前置条件和后置条件可查询。
- 每个模型 Step 的候选工具由当前本体状态生成。
- 每次工具调用都记录规则命中、许可结论、状态版本和结果回写。
- 提供最小 JSON-RPC/WebSocket API 和一个可查看轨迹、处理审批的 Web 页面。

## MVP 非目标

- 不追求 DSH 的全部包、全部 UI 或全部模型供应商兼容。
- 不实现动态自修改插件、LSP、E2B、Telemetry SaaS、会话全文搜索、语音和复杂附件。
- 不承诺多租户强隔离；本地沙箱只能作为文件副作用限制，不能代替容器或虚拟机。
- 不先做通用 OWL 全量推理器。MVP 使用面向 Action 的可版本化领域模型和确定性规则；RDF/OWL/SHACL/SPARQL 适配器在核心协议稳定后再增加。
- 不把 Workflow JavaScript 当成本体计划的权威。计划状态、依赖和补偿必须是可持久化数据。

## 代码仓库边界

新实现建议放在独立的 `ontology-agent` 工作区，不向 `deepseek-harness` 内写业务代码。建议结构如下：

```text
ontology-agent/
  apps/runtime/              # CLI、HTTP、WebSocket、进程生命周期
  apps/web/                  # Vue 管理界面
  packages/contracts/        # ID、事件、协议和错误
  packages/kernel/           # 插件、作用域、事件和卸载
  packages/session/          # 事件日志、投影和持久化
  packages/llm/              # 模型适配器
  packages/tools/            # 工具注册与执行管线
  packages/agent/            # Agent 接口、队列和循环
  packages/ontology/         # 本体、事实、策略和规划
  packages/subagent/         # 子 Agent
  packages/extensions/       # Goal、Todo、Plan、Jobs、Skills、MCP
  packages/protocol/         # JSON-RPC、SDK、ACP
```

这些是模块边界，不要求一开始就发布为大量 npm 包。第一版可以把相邻模块放在少量 workspace package 中，只有出现独立生命周期、独立协议或独立发布需求时再拆包。

## 版本路线

### M0：可测试内核

完成 03 至 05。所有 ID、错误、插件生命周期和事件日志可单元测试，不调用真实模型。

### M1：单 Agent 闭环

完成 06 至 11。能够运行一个带受控工具的持久会话，并从进程重启恢复。

### M2：本体约束闭环

完成 12 至 15。能够根据事实筛选工具、验证前置条件、执行、回写和补偿。这是第一个具有产品差异化的可演示版本。

### M3：长期任务与多 Agent

完成 16 至 23。补齐任务状态、后台执行、子 Agent、Workflow、Skills 和 MCP。

### M4：产品接入

完成 24 至 28。提供 API、SDK、Web 控制台、质量门禁和发布清单。

## 外部系统假设

旧报告提到 `euos-service-j` 和 `euos-vue`，但它们不在当前工作区。本计划只定义 `OntologyPort`、`BusinessToolPort` 和前端协议；接入 Java 服务或现有 Vue 页面之前，必须单独审计那两个项目的鉴权、事务、幂等键、错误码和领域模型，不能在本计划中臆造。
