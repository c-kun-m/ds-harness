# K02：错误模型、校验问题与异步调用栈

## 这一课解决什么

插件系统跨越 setup、依赖解析、事件、用户回调和异步清理。若所有失败都变成普通 `Error`，调用方无法判断应重试、回滚还是只记录；若清理错误覆盖主错误，真正原因会丢失；若异步边界没有调用位置，堆栈只指向 Promise 内部。

## 学习目标

- 设计稳定错误 code、phase、cause 和 context；
- 区分配置校验、生命周期状态、依赖缺失、用户代码和清理失败；
- 聚合多个校验 issue 并保留路径；
- 保留主失败，同时报告清理失败；
- 在不篡改原始 cause 的前提下补充异步调用位置。

## 错误分类建议

至少覆盖：

| 类别 | 例子 | 调用方策略 |
|---|---|---|
| CONFIG_INVALID | schema 问题、异步 schema 不支持 | 启动/更新失败，不重试 |
| INACTIVE_EFFECT | unloading/disposed 时注册 Effect | 编程错误或竞态，拒绝 |
| MISSING_SERVICE | required 服务未提供/未激活 | Fiber 等待或卸载 |
| DUPLICATE_SERVICE | 相同隔离键已占用 | provider 加载失败 |
| INVALID_PLUGIN | 不支持的插件形态 | 加载前失败 |
| USER_CALLBACK_FAILED | apply/listener/disposer 抛错 | 保留 cause，按阶段回滚 |
| CLEANUP_FAILED | 一个或多个清理失败 | 其余清理继续，聚合报告 |
| DISPOSED | 对已终止对象执行不允许操作 | 明确拒绝 |

名字可以不同，但语义不能全折叠成 UNKNOWN。

## 功能合同

- MUST：公共错误有稳定 code，不依赖完整 message 分类；
- MUST：保留原始 cause；
- MUST：包含能定位的 phase 和相关身份；
- MUST：ValidationError 保留所有 issue 的 path/message；
- MUST：主操作失败时，清理错误不得覆盖主 cause；
- MUST：只锁定稳定字段，堆栈和内部行号不是协议；
- SHOULD：异步包装能指出外层调用位置；
- MUST NOT：把敏感配置、token 或完整工具参数无条件放入错误。

## 实现任务

1. 定义内核错误基类和稳定 code 联合；
2. 定义 ValidationIssue/ValidationError；
3. 定义主失败 + cleanup failures 的组合规则；
4. 实现错误序列化记录，只包含允许字段；
5. 实现异步调用栈补充或操作位置记录；
6. 改造 K01 清理错误测试，断言 code/cause/聚合，而不是整段文本；
7. 为错误构造、包装、再包装和跨 async await 写测试。

## 测试矩阵

| 场景 | 断言 |
|---|---|
| 单一内核错误 | code/phase/id/cause 完整 |
| 多个 validation issue | 顺序与 path 保留 |
| 用户 Error 作为 cause | 对象身份或 cause 链保留 |
| 主 setup 失败 + 清理失败 | 主错误仍是主因，清理错误可访问 |
| 只有多个清理失败 | 稳定 CLEANUP_FAILED + 全部子错误 |
| async wrapper | 外层操作位置可诊断 |
| 重复包装内核错误 | 不丢原 code，不无限嵌套 |
| 序列化 | 无函数/stack/secret，仍可分类 |
| 事件 observer 失败 | 按事件合同隔离并记录 |

## 完成标准

- 所有 K01 清理失败使用统一错误模型；
- 主失败不会被清理失败覆盖；
- 错误记录可安全进入日志/协议；
- 你能说明哪些 listener 失败传播，哪些隔离。
