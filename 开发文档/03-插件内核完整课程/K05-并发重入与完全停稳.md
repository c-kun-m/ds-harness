# K05：并发清理、重入卸载与完全停稳

## 这一课解决什么

K04 能正确创建和回滚单个 Effect，但真实卸载同时面对多个 Effect、正在 setup 的 Promise、清理内部重入、observer 异常和重复 dispose。最危险的 bug 不是“某个清理没调用”，而是 dispose 已经兑现，后台清理仍在运行，随后继续修改已销毁状态。

## 两层清理顺序

必须区分：

1. **一个 Effect 内部**：它收集的 disposer 逆序串行执行；
2. **一个 Fiber 的多个 sibling Effect**：owner 逆序取得当前 Effect 集合，但可以同时启动并用 `Promise.all`/settled 等待。

这样既保留局部依赖顺序，又避免无关资源的慢清理阻塞全部 sibling。

## cleanup inertia

当公开 disposer 已开始清理，Fiber 随后进行结构化卸载时，Fiber 不能认为该 Effect 已消失就直接结束。owner 必须能“加入”已经运行的清理事务，直到它完全停稳。

这需要区分：

- 逻辑上已从 active collection 删除；
- 清理事务仍在运行；
- 结构 owner 仍需等待的 inertia。

## 功能合同

- MUST：同一 Effect 的清理至多启动一次；
- MUST：所有竞争调用者等待同一清理结算；
- MUST：Fiber unload 等待 setup barrier 和所有 cleanup inertia；
- MUST：sibling Effect 可并发清理，各自内部仍逆序串行；
- MUST：一个 sibling 失败不阻止其他 sibling 清理；
- MUST：重入 dispose/unload 不死锁、不递归启动第二事务；
- MUST：UNLOADING 状态先关闭准入，再取得当前 Effect 批次；
- MUST：dispose 兑现后不会再有该 Fiber 的清理/observer 修改；
- SHOULD：多个清理错误全部可诊断，生命周期可按策略记录而不阻止终态。

## 你先做的设计题

1. public disposer 先把记录从 owner Map 删除再 await 清理，Fiber 如何找到运行中的 Promise？
2. Effect A 的 disposer 调用 `fiber.dispose()`，而 Fiber 正在等待 A，如何避免自等待死锁？
3. sibling A 永不响应取消，dispose 是否可以永远等待？超时属于内核还是上层策略？
4. owner 逆序取得 Effect 后并发启动，逆序还有什么可观察意义？

## 实现任务

1. 为每个 Effect 建立唯一 cleanup transaction；
2. 建立 owner 可加入的 inertia 表/弱映射；
3. Fiber unload 先原子关闭准入并快照 Effect；
4. 按逆序启动 sibling 清理并并发等待；
5. 隔离/聚合每个 sibling 失败，保证全部启动；
6. 处理 cleanup 内重入 public dispose/fiber unload；
7. 为完全停稳增加测试探针：active effects、inertia、pending setup 都为空。
