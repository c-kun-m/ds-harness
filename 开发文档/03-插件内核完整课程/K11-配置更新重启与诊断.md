# K11：配置校验、依赖 epoch、更新、重启与诊断

## 这一课解决什么

插件不是只加载一次。配置变化、required provider 世代变化、显式 restart 都可能触发卸载再加载。若更新过程中旧/新配置混用，或 stale apply 在卸载后仍继续执行，就会出现两个世代同时修改服务。

## 配置合同

插件可以提供 Standard Schema 兼容的同步校验器。固定基线拒绝异步 schema 结果，因为 Fiber reload 的配置决定需要同步稳定。ValidationError 要保留全部 issue 路径。

解析后的配置属于当前 epoch；不要让调用方后续修改原始对象影响运行实例。

## Epoch

epoch 用于表达“这次加载依赖的世界”：至少包含 required provider Fiber uid/世代和本次配置修订。若加载等待期间 epoch 改变，旧执行不得发布 ACTIVE，需要丢弃/卸载并按新 epoch 重试。

## update/restart 区别

- `update(config)`：经过 `internal/update` waterfall，插件/扩展可以校验或转换；若有效配置改变，触发安全 reload；应返回 waterfall 的权威结果；
- `restart()`：配置不变，显式创建新运行世代；
- dependency refresh：由 service notify 驱动，required epoch 改变后 reload。

## 功能合同

- MUST：配置在运行用户 apply 前同步校验；
- MUST：异步 schema 结果明确拒绝；
- MUST：ValidationError 保留 paths/issues；
- MUST：同一时刻每个 Fiber 只有一个可发布 epoch；
- MUST：stale 加载结果不能进入 ACTIVE；
- MUST：update/restart 复用完全停稳的 unload；
- MUST：并发更新按明确策略串行/最后写入获胜，不能交错发布；
- MUST：update waterfall 的返回值是权威更新结果；
- MUST：状态、配置、服务和插件诊断 observer 失败被包含；
- SHOULD：诊断树显示 uid、state、epoch、plugin、依赖、effect labels 和最近错误。

## 测试矩阵

| 场景 | 预期 |
|---|---|
| 有效配置首次加载 | apply 收到冻结/隔离后的解析值 |
| 多 issue 无效配置 | apply 不运行，issues 完整 |
| schema 返回 Promise | 明确拒绝 |
| update 同值 | 按合同 no-op 或可观察结果，不多余 reload |
| update 新值 | 旧世代停稳后新世代 ACTIVE |
| waterfall 转换/拒绝 | 返回权威结果，拒绝时旧实例保留 |
| 并发 update A/B | 最终配置和世代确定，无交错副作用 |
| 加载中 provider epoch 改变 | stale apply 不发布 |
| restart | 配置不变，运行世代变化 |
| FAILED restart | 最近错误更新，成功可恢复 |
| observer 抛错 | 更新/卸载仍停稳 |
| diagnostic snapshot | 无活动能力泄漏，身份/状态一致 |
