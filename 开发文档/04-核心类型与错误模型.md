# 核心类型与错误模型

## 目标

在写会话和模型逻辑前固定跨模块协议，避免后续把 Session ID、Tool Call ID、Job ID 和普通字符串混用，也避免每个模块创造自己的取消和错误格式。

## 前置条件

完成 [工程骨架与插件内核](03-工程骨架与插件内核.md)。

## 必须定义的类型

- `Branded<Name>` 以及 `SessionId`、`MessageId`、`CallId`、`ToolName`、`JobId`、`OntologyVersionId`、`FactId`、`ActionId`、`PlanId`、`ExecutionId`。
- `JsonPrimitive`、`JsonValue`、`JsonObject` 和 `assertLosslessJson()`。
- `ContentBlock`：MVP 先实现 `text`、`reasoning`、`tool-call`、`tool-result`；附件后加，不提前污染核心。
- `UserMessage`、`AssistantMessage`、`ToolResultMessage`，每条消息都有不可变 `MessageId`。
- `TokenUsage`、`FinishReason`、`LlmFailure`、`TurnEndReason`。
- `RuntimeError`：`code`、`message`、`details?`、`retryable`、`cause?`，跨进程时只发送 JSON 字段。
- `Deadline` 和取消原因：human、timeout、parent、shutdown、policy。

## 错误分类

| 类别 | 示例 | 默认处理 |
|---|---|---|
| 配置错误 | 重复工具名、未知 Provider | 启动失败，不重试 |
| 输入错误 | 工具参数不符合 Schema | 生成失败的工具结果，不执行工具 |
| 策略拒绝 | 本体前置条件不满足、审批拒绝 | 生成可审计拒绝结果，不抛出进程错误 |
| 瞬时基础设施错误 | 429、连接重置 | 由明确重试策略处理 |
| 不确定副作用 | 进程崩溃时工具已开始但无结果 | 标为 `outcome-unknown`，禁止自动重复非幂等调用 |
| 完整性错误 | 事件 seq 断裂、日志格式未知 | fail closed，拒绝恢复 |
| 取消 | 用户、父任务、超时、关闭 | 保留结构化原因，传播到已开始工作 |

## 手写顺序

1. 写 brand、JSON 类型和 `assertNever`。
2. 写消息和内容块联合类型。
3. 写错误基类、错误码目录和序列化函数。
4. 写 `AbortSignal` 合并、Deadline 计算和 timeout helper。
5. 为所有外部输入建立 Zod Schema，并在测试中验证 TypeScript 类型与 Schema 语义一致。

## 关键不变量

- 事件、RPC、数据库 JSON 字段都必须通过 lossless JSON 检查。
- 错误码稳定，错误消息可改；客户端只按 code 分支。
- 超时是绝对 deadline，向下游传递剩余时间，不能每层重新获得完整超时。
- 取消不等于失败；取消原因不能被包装成 `UNKNOWN`。

## 测试与完成标准

用属性测试生成任意 JSON 值并完成序列化往返；拒绝 `undefined`、BigInt、循环对象和非有限数字。证明不同 brand 不能在 TypeScript 编译期互换，并证明跨 RPC 的错误能保留 code、retryable 和 details。
