# 07：工具注册、作用域可见性与权威执行管线

## 本课定位

工具是模型触达副作用的唯一入口。Schema 可见不代表允许执行；隐藏工具也不能被模型用旧名称直接调用；策略、审批、Guard、执行、后处理和定稿必须只有一条权威路径。MCP、Workflow、PTC 子调用以后都重新进入这条管线。

## 学习目标

- 建立作用域分层的 ToolDefinition Registry；
- 从类型化 schema 产生协议 schema，并在执行前严格验证；
- 区分可见性、pre decision、单调 guard、around dispatch、post policy、finalize 和 result observer；
- 正确处理取消、超时、未知工具和用户异常；
- 将并行只限制在 execution body，按模型顺序提交结果；
- 保证每次 call 恰好一个冻结的权威结果。

## ToolDefinition 合同

定义至少包含：name、description、参数 schema、输出 schema/规范值、execute、executionMode classifier，可选声明式 timeout、finalizeContent 和纯展示意图。

需要区分：

- canonical value：程序化/PTC 调用方使用的 lossless JSON；
- model content：文本/图片等模型可见投影；
- UI presentation：纯派生，不参与执行真相；
- `timeoutMs` 声明：除非 timeout policy wrapper 强制，否则不自动生效。

## 作用域与可见性

- 全局层 + Scope/Agent layers；
- nearest scope 同名 shadow；同层重复明确失败；
- restrict allow/deny 取交集，生命周期随 Scope；
- `schemas(scope)` 只暴露模型可见字段，不泄漏 execute/finalizer；
- 执行查找使用同一 scope/restriction；被隐藏工具直接点名仍返回 UNKNOWN/NOT_VISIBLE。

## 权威流水线

```text
resolve definition and scope
→ parse + validate arguments（冻结）
→ tools/pre-execute waterfall（allow/deny/ask）
→ monotonic guards（只能新增拒绝）
→ fuse caller-owned signal again
→ tools/execute around waterfall
→ definition.execute
→ tools/post-execute waterfall（检查/替换/上下文）
→ definition.finalizeContent（只在权威结果仍允许时）
→ freeze final result
→ tools/result observer
```

`pre-execute` 不应偷偷改写 arguments，否则日志/展示参数与实际副作用分叉。若确需变换，建立明确的新 canonical arguments 事件/合同。

## 决策和失败

- ask 无 approval service/responder 时 fail-closed；
- guard 同步、单调，后续 guard 不能推翻已有拒绝；
- 未知工具、非法参数、用户 execute throw 都转为结构化失败结果，不让整个 Agent Loop 崩溃；
- pre/around/post 基础设施失败有独立 code；
- 调用前取消 → ABORTED_BEFORE_DISPATCH；
- body 后取消只在没有更具体失败时将成功替换为 ABORTED；
- TOOL_TIMEOUT 等具体结果优先于晚到取消；
- result observer 只观察冻结结果，不能改写。

## 并发调度

工具定义/运行时 classifier 返回 `parallel-safe` 或 `exclusive`。连续 safe 调用进入有界池；exclusive 前后形成屏障。关键顺序：

- 策略准入按模型顺序；
- safe body 可以重叠；
- result policy/Session commit 按模型顺序；
- 取消时未分发调用合成 ABORTED_BEFORE_DISPATCH；
- 已分发调用收到 signal 并等待停稳；
- classifier 异常按保守 exclusive 或明确失败，策略要固定。

## PTC 边界

完整复刻可在后续加入 `native/ptc/both`。PTC 的 `run_code` 内部工具绑定必须重新进入完整 ToolRuntime；纯 ptc 下，未公开的工具直呼要在策略前拒绝。中间结果仅存在执行局部，外层结果才进入 Session。

## 实现任务

1. Tool schema/definition/result 类型；
2. ScopedLayers Registry 和 restrict；
3. 参数校验与 canonical snapshot；
4. pre/guard/execute/post/finalize/result 管线；
5. signal/deadline 和稳定错误映射；
6. execution mode classifier 与有界调度接口；
7. Session call/result commit adapter；
8. echo/fail/slow/read-only/mutating 假工具测试；
9. PTC 延后时写差异账本，不假装已完成。

## 测试矩阵

| 场景 | 必须观察到 |
|---|---|
| scope shadow/restrict | schema 与执行查找一致 |
| unknown/hidden | body 不运行，稳定结果 |
| 非法 JSON/schema | body/审批/guard 均不运行 |
| pre deny/ask | fail-closed 且审计可见 |
| 多 guard | 任一拒绝后不能被放行 |
| around wrapper | 洋葱顺序、signal 不可丢 |
| body throw | 结构化工具失败，不崩 Loop |
| post replace/reject | 最终结果唯一 |
| finalizer | 只对权威 canonical result 定稿 |
| result observer throw | 结果不被改写，错误按合同隔离 |
| 调用前/执行中/执行后取消 | 三阶段语义正确 |
| timeout 与 abort 竞争 | 更具体结果优先 |
| safe/exclusive 序列 | body 重叠、提交仍模型序 |
| 并发上限 | 不超池，后项最终运行/取消 |
| old disposer | 不删除新同名工具 |

## 完成标准

- 所有调用只有一个权威 final result；
- 隐藏工具无法绕过可见性；
- signal 在任何 around wrapper 后都仍是调用方拥有的融合信号；
- safe/exclusive 调度有确定性交错测试；
- PTC/MCP/Workflow 未来接入点只允许调用 ToolRuntime。
