# 13：本体定义、事实快照与事务存储

## 本课定位

这是本项目原创领域层，不是 DeepSeek Harness 原有模块。DSH 提供生命周期、Session、Tools 和恢复边界；本课建立可版本、可验证、可查询的领域模型与事实状态，为 14 的确定性策略和 15 的计划回写提供真源。

MVP 不实现通用 OWL/RDF 推理器。目标是面向业务 Action 的强类型模型、受限规则和一致快照；以后可以通过 adapter 接 RDF/OWL，但不能因此跳过事务、版本和审计合同。

## 学习目标

- 将定义版本与运行事实版本分开；
- 发布前完整验证实体、关系、约束和引用；
- 从一个原子 FactSnapshot 进行查询和策略判定；
- 用 CAS/事务防止并发写丢失；
- 保留事实来源、有效时间、撤回与历史；
- 用 transactional outbox 连接领域事务和 Session 审计；
- 对敏感属性建立字段级视图，不让模型/普通日志读取原值。

## 领域定义

### OntologyVersion

至少包含：id、semanticVersion、state（draft/active/retired）、canonical content hash、createdAt、previousVersion、兼容性说明。draft 可编辑；发布后不可原地修改，任何改变产生新 id/hash。

hash 必须基于规范序列化：字段顺序、默认值、数组顺序和 Unicode 规则确定。不能直接对普通对象 `JSON.stringify` 后假设跨实现稳定。

### EntityType

- stable type id；
- 属性：类型、required、默认、敏感标签、可空性；
- 唯一键/业务键；
- 可选父类型；
- 允许的状态/值约束。

继承必须无环，属性覆盖要遵守可替换规则：子类型不能无说明地放宽/收紧到让父查询失真。

### RelationType

- stable relation id；
- from/to 类型和是否接受子类型；
- 方向与反向名（若有）；
- 基数（0..1、1、0..n、1..n 等）；
- 删除/retract 策略；
- 是否允许重复边、自环。

### Constraint

MVP 支持 required、enum、range、pattern、unique、relation cardinality 和受限表达式 AST。自定义约束是受信任纯函数插件时，必须版本化并且不能执行 I/O；优先使用可序列化 AST。

## 运行事实

### Entity/Relation Instance

实体至少有 id、typeId、properties、revision、validFrom/validTo、state。关系有 relationId、from/to、revision、有效区间和状态。物理删除不是默认操作；retract/tombstone 保留历史。

### Fact

若采用三元组/标量 Fact 层，至少保留：subject、predicate、object/value、source、confidence（若业务需要）、ruleId（推断时）、revision、valid interval、asserted/retracted。

原始事实和推断事实分开存来源。推断不能覆盖人类/业务系统断言；规则失效时撤回自己的推断，不删除原证据。

### FactSnapshot

Snapshot 是 `{ ontologyVersion, factRevision, readToken }` 的原子视图：

- 同一次策略评估所有查询来自它；
- 不跨 revision 拼接多个查询结果；
- Snapshot 生命周期/事务边界明确；
- 执行时将 revision 传给 CAS；
- 过期 Snapshot 仍可读其历史视图（若合同允许），但不能无条件写。

## 存储边界

### OntologyRepository

- create/update draft；
- validate draft，返回全部结构问题；
- publish，原子生成 immutable version/hash；
- get/list/version lineage；
- retire，不删除历史。

### FactStore

- begin/read Snapshot；
- get/query entity/relation/fact；
- apply mutation batch with expected revision；
- append history 和 outbox 同事务；
- 读取当前视图与指定 revision 历史视图；
- 敏感字段只经授权 view 解密/展开。

### OntologyQuery/Port

Query 在显式 Snapshot 上做类型、属性、关系和受限条件查询；Port 把 repository/store/query 组合为可替换能力。远程实现必须保留 snapshot token、CAS、幂等和错误语义，不能只提供一组最终一致 REST 查询冒充相同合同。

## 发布期验证

一次 validate 至少检查：

- ID 格式/唯一、所有引用存在；
- 继承无环、属性覆盖兼容；
- relation 两端类型/基数合法；
- constraint AST 可解析、类型正确、无未知操作；
- unique key 引用合法且不含禁止字段；
- Action 引用可在 14 的联合发布时检查；
- canonical hash 可重复计算。

返回全部 issue path，而不是遇到第一项就停止。

## 事实事务与 Outbox

领域状态是真源，Session 是某个 Agent 执行的审计。跨数据库不能“先更新事实，再尽力 append Session”。正确边界：

```text
begin domain transaction at expected factRevision
→ validate mutation + constraints
→ write current rows + append history
→ write outbox record（包含 execution/decision/session identity）
→ commit and advance factRevision
→ dispatcher idempotently appends ontology/facts-committed to Session
→ mark outbox delivered
```

重复 dispatcher 不重复应用事实变化；Session 事件需要稳定 outbox id 进行去重/关联。若 Session 长期不可用，领域事务仍然成功但审计投递处于明确 pending，不可伪称已完全同步。

## 敏感数据

- schema 标注 sensitive/secret/PII；
- 默认 query view 对模型和普通诊断做 redaction/omission；
- Policy 可使用必要派生布尔/分类，不把原值写进 decision event；
- 加密存储、密钥管理属于 provider；
- 访问敏感 view 本身需要权限和审计；
- hash 也可能泄露低熵秘密，不能一律安全。

## 迁移

发布新版本先生成兼容性报告：新增 required、类型收窄、关系基数收紧、删除属性/类型等。MVP 不自动迁移不兼容实例；迁移是版本化、可恢复的独立任务。旧事实必须能说明基于哪个 ontology version 写入/解释。

## 实现任务

1. 定义可规范序列化的 ontology schema；
2. 实现 draft validator 和 canonical hash；
3. 实现 immutable publish/retire/lineage；
4. 实现内存 FactStore、Snapshot 和 CAS；
5. 实现 SQLite transaction/current/history；
6. 实现 query evaluator 和敏感 view；
7. 实现 outbox/dispatcher/idempotency；
8. 实现兼容性报告；
9. 用“工单—负责人—状态”本体做完整演示。

## 测试矩阵

| 场景 | 必须观察到 |
|---|---|
| 引用缺失/继承环/类型冲突 | 全部 issue + path |
| canonical equivalent input | 相同 hash |
| 发布后修改原对象 | 已发布 version 不变 |
| 同 revision 并发 CAS | 恰好一个成功，另一个 conflict |
| Snapshot 中并发写 | 旧 Snapshot 查询自洽，新 Snapshot 见新值 |
| unique/cardinality violation | 事务回滚，revision 不前进 |
| retract/推断撤回 | 历史保留，原始事实不被覆盖 |
| outbox append 失败/重试 | 事实不重复，最终事件一次可关联 |
| 进程崩溃在 commit 后投递前 | 重启后继续 outbox |
| 敏感字段 | 模型 context/decision/普通日志无原值 |
| 不兼容新版本 | 报告阻止静默解释/自动迁移 |
