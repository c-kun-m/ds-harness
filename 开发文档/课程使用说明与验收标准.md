# 课程使用说明与验收标准

本文件规定所有课时共用的学习方法和完成标准。每个模块只写自己的特殊合同，不重复解释“什么叫完成”。

## 1. 你在复刻什么

复刻目标不是上游的目录、类名或每一行代码，而是固定版本对外可观察的核心行为：

- 调用者能使用的 API 和类型约束；
- 状态何时变化，变化是否可被事件或查询观察；
- 同步失败、异步失败、取消、并发和重入时发生什么；
- 哪个对象拥有哪个资源，谁负责释放，何时算完全停稳；
- 持久日志、投影、工具结果和协议载荷的顺序与边界；
- 上游测试锁定的安全与兼容行为。

你可以采用不同的内部结构，但不能在没有记录的情况下改变这些行为。

## 2. 每课的七遍学习法

### 第一遍：只看问题

先回答：如果没有这个模块，系统会出现什么真实故障？写出至少三个失败场景。不要先看上游类名。

### 第二遍：提取功能合同

把文档中的 MUST、MUST NOT、SHOULD 转成自己的验收清单。区分：

- 输入合同：允许什么，拒绝什么；
- 输出合同：返回值和错误的稳定形状；
- 时序合同：什么时候可见，什么时候可释放；
- 所有权合同：谁创建、谁发布、谁撤销；
- 停稳合同：Promise 兑现时还有没有后台工作。

### 第三遍：画模型

至少画一张图：状态图、序列图、所有权树或数据流图。图不是装饰，它应该能回答“此时失败会由谁回滚”。

### 第四遍：先写黑盒测试

先用公共 API 写最小失败测试，再写实现。不要为了测试私有字段而暴露内部状态；需要观测时，优先通过事件、日志、查询或受控测试探针。

### 第五遍：独立实现

只看本课“实现任务”，自己决定文件和数据结构。此时不要逐行照抄上游。对你无法确定的行为，先在差异账本中写假设。

### 第六遍：读上游源码与测试

按“源码地图”顺序阅读：公共类型 → 主路径 → 错误/清理路径 → 测试。比较的是行为与不变量，不是代码长相。

### 第七遍：差异复盘

逐项填写差异账本，并用自己的话回答课末问题。不能解释的通过项视为“偶然通过”，不能毕业。

## 3. 差异账本

每个模块在自己的目录中维护 `PARITY.md`，推荐表格：

| 编号 | 上游行为 | 本项目状态 | 证据 | 决定 |
|---|---|---|---|---|
| E-01 | 重复 disposer 不重复副作用 | 通过 | `effect.spec.ts` 测试名 | 保持 |
| E-02 | async generator 可逐项注册清理 | 未实现 | 缺测试 | K04 前补齐 |
| E-03 | Fiber sibling effect 并发清理 | 有意差异 | 设计记录链接 | 暂时串行，不能声称完整复刻 |

状态只能使用：

- `通过`：黑盒行为等价且有自动测试；
- `有意差异`：明确描述影响、理由和重新评估点；
- `未实现`：课程合同要求但尚未完成；
- `不适用`：上游产品表面不属于本项目，并说明为什么不影响核心。

## 4. 测试矩阵

每个核心模块至少覆盖以下维度。没有相关行为时写“不适用”和理由，不能直接删列。

| 维度 | 需要证明什么 |
|---|---|
| 正常路径 | 单次调用得到正确状态和结果 |
| 边界输入 | 空集合、首项、末项、最大值、缺省值 |
| 非法输入 | 在副作用前失败，错误可分类 |
| 同步失败 | 已完成的局部工作被回滚 |
| 异步失败 | Promise 拒绝被观察，资源最终释放 |
| 取消 | 取消前、分发前、执行中、提交前分别有确定结果 |
| 重复调用 | dispose/cancel/finish/retry 是否幂等或明确拒绝 |
| 并发 | 多调用交错不破坏顺序、身份和所有权 |
| 重入 | 回调内触发卸载、更新或再次调用不形成悬挂状态 |
| 组合 | 父子作用域、多个插件或多个提供方相互作用正确 |
| 故障注入 | 日志、清理、监听器、外部 I/O 失败时仍可停稳 |
| 泄漏 | 监听器、Timer、Abort listener、子进程、Promise 无残留 |
| 回放/恢复 | 适用时，从相同日志得到相同视图 |
| 上游等价 | 固定版本代表性测试被移植为黑盒测试 |

异步测试不要依赖任意 `setTimeout(100)` 猜测顺序。使用 deferred promise、barrier、受控 scheduler 或 fake timer 明确控制交错点。

## 5. 错误验收

错误不仅是一段文本。至少检查：

- 稳定的错误类别或 code；
- 原始 cause 是否保留；
- 操作身份、模块和阶段是否能定位；
- 失败发生前是否已经发布了不可撤销状态；
- 清理失败是否覆盖主失败，还是被聚合/记录；
- 错误被谁观察，是否存在未处理 Promise rejection；
- 错误是否会错误触发重试或重复副作用。

测试不要锁死整段运行时堆栈，只断言稳定字段和必要消息片段。

## 6. 所有权与完全停稳

文档中的“dispose 完成”统一表示：

1. 不再接受新工作；
2. 已接收工作完成、失败或收到取消；
3. 所有清理 Promise 已被等待；
4. 子资源已经释放；
5. 监听器、计时器和 Abort handler 已解除；
6. 外部观察者不会再收到该实例的新事件。

仅仅发出 `abort()` 不等于停稳；仅把状态改为 `disposed` 也不等于停稳。

对每个活动对象回答四个问题：

- 谁在发布前拥有它？
- 发布的原子边界是什么？
- 发布后由谁持有 disposer/handle？
- 创建、发布通知或释放失败时由谁兜底？

## 7. 并发与顺序

看到 `Promise.all` 不等于“整个流程并发”。必须标注并发域：

- Cordis 中，一个 Effect 收集到的 disposer 逆序串行；一个 Fiber 的多个 sibling Effect 在卸载时可以并发等待；
- Agent 工具中，策略准入和最终提交保持模型顺序，只有允许重叠的执行主体并发；
- 持久化中，事件可先进入内存日志，但 durability barrier 必须等待对应批次安全落盘；
- Workflow 中，脚本可以并发等待多个子 Agent，但事件配对和 run ownership 仍需确定。

每个并发实现都要写清楚：启动顺序、完成顺序、提交顺序、失败聚合、取消传播和最大并发数。

## 8. 文档中的规范词

- **必须 / MUST**：不满足就不是本课目标的正确实现；
- **禁止 / MUST NOT**：违反会破坏核心不变量；
- **应该 / SHOULD**：默认遵守，偏离需要写原因；
- **可以 / MAY**：内部实现可选，不影响行为等价；
- **上游事实**：固定提交源码或测试能直接证明；
- **课程取舍**：本项目主动选择，不能冒充上游事实；
- **本体扩展**：DSH 没有的领域能力。

## 9. 单课毕业条件

只有同时满足以下项目才能进入下一课：

- 功能合同中的 MUST 全部有测试；
- 测试矩阵没有无解释空项；
- 差异账本没有未说明的行为漂移；
- 类型检查、单测和相关集成测试通过；
- 失败后无未处理拒绝和资源泄漏；
- 能从状态、所有权和时序解释实现；
- 已提交一次只包含本课改动的 Git commit。

## 10. 模块评审评分

每项 0–2 分，总分至少 16/20，且“所有权与停稳”“失败/取消”不得为 0。

| 项目 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 合同完整 | 只有快乐路径 | 主要合同齐 | 边界和限制也清楚 |
| 状态模型 | 隐式布尔值 | 有状态但转移松散 | 封闭状态与合法转移 |
| 所有权与停稳 | 有泄漏/悬挂 | 普通路径可释放 | 创建、失败、重入均停稳 |
| 失败/取消 | 吞错或混乱 | 基本可分类 | 每阶段有稳定语义 |
| 并发顺序 | 靠时序碰运气 | 有互斥/队列 | 并发域和提交序明确 |
| 测试 | 只测演示 | 正常+边界 | 故障、并发、重入、泄漏齐 |
| 上游等价 | 未对照 | 人工阅读 | 自动 parity + 差异账本 |
| 可诊断性 | 无身份/阶段 | 有消息 | code/cause/身份/阶段完整 |
| 代码边界 | 大类包办 | 基本分层 | 合同、机制、产品表面分开 |
| 解释能力 | 只会描述代码 | 能说主流程 | 能推演任意失败点 |

## 11. 什么时候暂停实现

出现以下情况先回到设计，不继续堆代码：

- 一个 `dispose()` 同时负责状态修改、日志、网络和多层清理，却没有明确所有者；
- 为修复竞态不断增加布尔值，已经说不清合法组合；
- 测试必须 `sleep` 才能通过；
- 旧 disposer 能删除后创建的同名注册；
- 失败只能靠日志文本判断，调用方没有稳定 code；
- 恢复依赖“猜最后发生了什么”，而不是日志中的明确证据；
- 本体策略只存在 Prompt 中，执行前没有确定性 Guard；
- 为了通过演示绕过工具管线、Session 或权限层。
